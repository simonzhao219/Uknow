# 文件內容守則:不記錄不存在的功能

規則本體只在這裡寫一份。`docs/README.md`〈慣例〉與規格書 §14 開頭
只放指標,不重複規則內容(見「規則只寫一份」)。機械輔助見下方,是
advisory,不是硬擋。

## 為什麼

PR #118、#119 都出現過同一個模式:規格書 §14「已知落差」清單移除一列
時,額外在文件裡補寫「已定案不提供 X、非落差」之類的旁白,重複強調
某功能不存在。這個反模式後來在 develop 上被更完整地清理過一次
(PR #117/#122),但那次清理也只修了症狀——連清理本身都漏掃了一處
(PR #117 徹底清乾淨規格書,還是漏了 `e2e/journey/README.md`,得靠
PR #122 補)。

問題不是沒有意識到——PR #119 內部曾自我糾正一次,commit message 已經
講出和這條規則幾乎一樣的道理,但糾正只綁定當下那個 diff,沒有推廣成
同類掃描,也沒有把悟出的原則寫進任何未來 session 讀得到的地方,於是
同一個模式後來又發生了一次。這份檔案(path-scoped,動 `docs/`、
`e2e/**/*.md`、`e2e/**/*.feature` 時自動載入)就是補這個「悟出的原則
沒有沉澱」的缺口。

## 規則

**沒有的功能,不必記錄「沒有」。** 落差消除或功能定案不做時,把該列
從規格書 §14 刪除即可(§14 開頭已寫明);不要在刪除處或其他文件另外
補一段「已定案不提供 X、非落差」之類的旁白。功能不存在,文件裡不出現
這個條目就是正確狀態——反覆解釋「為什麼沒有」,等於在維護一份原則上
列不完的「不提供清單」。

**例外:程式碼裡仍留著容易被誤讀的殘跡**(保留但不再讀寫的欄位、已停用
的路由),才在該殘跡定義處寫一次**最小事實**說明,不重複寫進第二份
文件——例如 `subscriptions.is_canceled` 的 vestigial 語意寫在該欄位的
migration column comment 裡即可,規格書不必再抄一份。

**同一原則已用於 `docs/plans/` 的鷹架文件生命週期**——內容刪除不等於
遺失,`git show <hash>:<path>` 永遠取得回。

## 機械輔助(advisory,非硬擋)

`scripts/git-hooks/pre-commit` 掃 staged 的 `docs/**/*.md`、`e2e/**/*.md`
新增行,命中「已定案不提供/已定案的產品決策/非落差/不必再列為待實作」
就印提醒,不擋 commit——§14 表格本身合法會出現「未實作」字樣,上面的
例外條款也合法需要類似措辭,關鍵字比對分不出語意,硬擋只會製造假陽性、
逼人繞過閘門。
