# /fix-bug — 缺陷修復流程

「哪裡壞修哪裡」是缺陷修復的預設失敗模式:症狀消了、根因還在、
同病灶的兄弟們排隊等著壞。本流程強制走完根因與同類掃描才准收工。

## 0. 分級(比例原則——不是每個 typo 都值得全套)

- **表層錯**(typo、顯見筆誤、單點顯錯且根因自明):簡版=重現測試→修
  →綠→防線回填一句話。不建 fix 目錄,commit message 交代即可
- **行為級 bug**(行為與預期不符、資料錯、間歇性、金流/會籍相關一律):
  完整版,走以下全部步驟,狀態記入 `docs/plans/fix-<slug>/fix.md`
  (從 `docs/_templates/fix.md` 實例化)

拿不準就走完整版——分級錯誤的成本不對稱(漏掃同類 >> 多花十分鐘)。

## 完整版步驟

1. **重現**:先寫紅燈測試釘住 bug(落點依 CLAUDE.md 測試版圖選層)。
   寫不出重現測試=還不理解 bug,禁止動手修。之後進入標準 TDD 紅燈期
   (`touch .claude/tdd-lock` → commit `test(red)`,相位鎖照常生效)
2. **根因分析**:症狀 ≠ 根因。連問:為什麼會發生?為什麼當時沒被發現?
   追到機制層(空值路徑?競態?錯誤假設?規格誤讀?),寫入 fix.md
3. **同類掃描**:把根因抽象成 pattern,grep/audit 全 codebase 找同病灶
   (例:hooks 順序 bug → 掃所有 route guard;空值崩潰 → 掃同一資料源
   的所有消費者)。找到的:小則本次一併修,大則記入 friction-log 排償還
4. **四面向審視修法**(修「對」而不只是修「掉」):
   - 系統:別處是否依賴同樣的錯誤假設?修了這裡會不會壞那裡?
   - 架構:這是點狀 bug 還是架構缺陷的症狀?後者 → 停,升級走
     `/plan-feature` 做結構修正,不要在爛地基上補洞
   - UIUX:錯誤是不是 UX 設計誘發的(使用者被引導做出壞輸入)?
   - 需求:「正確行為」規格書是否根本沒定義?是 → 列開放問題求人裁決
   輕量做法:自問自答寫入 fix.md;重大 bug(金流/資料/安全)則派
   四個 plan-reviewer agent 審 fix.md 的修法節
5. **TDD 修復**:實作至綠 → `scripts/tdd-unlock.sh` → commit `fix:`
6. **防線回填**(第五問,免費的診斷):這個 bug 為什麼 CI/hook/測試
   都沒攔到?攔得到 → 補閘門(缺測試層?缺 lint 規則?);攔不到 →
   記 friction-log 一句話。每個漏網 bug 都是框架的免費體檢
7. 分支 `fix/<slug>`,PR → develop,照 PR 範本;push 後 `gh pr checks` 盯綠
