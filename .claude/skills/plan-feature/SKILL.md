# /plan-feature — 規劃階段

本階段**只規劃不實作**——規劃與實作硬性分離,是因為混在一起時模型會傾向
邊想邊寫、規劃淪為事後追認。

## 0. 先決定要不要落檔(預設:不落檔)

規劃檔是**鷹架不是文件**:施工期有用(跨 session 接手、守衛判斷、人審留痕),
上線後價值急降——程式碼與測試才是真相,舊 plan 只會被誤當規格。所以:

**預設走 Plan Mode**:規劃內容留在對話裡,不寫進 repo。適用於需求明確、
一條對話做得完的改動。分支用 `fix/*` 或 `claude/*`(**不要用 `feature/*`**
——那會觸發需要規劃檔的守衛)。

**符合以下任一才落檔**到 `docs/plans/<slug>/`:
- 做不完要跨 session/跨天(web session 容器是拋棄式的,**git 是唯一能跨
  session 的通道**)
- 動到金流、資料正確性、會籍(錯了不可逆,需要人審留痕)
- 階段數 ≥3(TDD 進度需要外部記憶抗 compaction)

拿不準就落檔——事後刪很便宜,中途才發現接不下去很貴。

## 步驟(兩種模式共用)

1. **先讀再想**(順序刻意:需求 → 現況 → 才有資格設計):
   - `docs/uknow-software-specification.md` 中與 $ARGUMENTS 相關的章節
   - 動 UI 就再讀 `docs/ui-ux-guidelines.md` 對應段落
   - 探索會被動到的 src/supabase 模組(用 Grep/Read,不要憑印象)
2. **依四面向規劃**:結構照 `docs/_templates/plan.md` 的節次(使用者需求 /
   系統設計 / 架構影響 / UIUX / 階段切分 / 開放問題 / 風險回滾)。
   填寫密度看 `examples/plan-example.md`——它示範的是「一句話講清楚」的
   高度,不是愈長愈好。**落檔模式**才把它寫成檔案:
   `docs/plans/<slug>/plan.md`,且 **`<slug>` 必須等於之後的分支 slug**
   (`feature/<slug>`)——守衛靠這個對應找規劃書。
3. **階段切分是給 TDD 用的**:每階段一個紅綠循環、有明確測試落點與驗證
   標準——切不出測試落點的階段代表設計還沒想清楚。
4. **開放問題是逃生口**:規格書模糊、兩案難決、需要商業判斷的,列成
   「開放問題」等人裁決。**禁止腦補需求**——每個斷言都要能指出依據
   (規格書章節或 codebase 現況)。
5. **落檔模式的收尾**:同時從 `docs/_templates/progress.md` 實例化
   `docs/plans/<slug>/progress.md` 並預填階段清單(狀態全部「未開始」)
   ——rehydrate 鏈從這裡開始,現在不建,鏈就是斷的。
6. **接著跑 `/review-plan`**——規劃完就審查,不要等人開口。規劃書自己寫完
   自己看不出問題,這是確認偏誤,四個獨立視角才看得見。落檔模式傳 slug;
   Plan Mode 則把規劃全文交給它(它支援 inline)。
7. **絕不寫任何實作**。審查報告出來後停,等人裁決;實作只能由人親自打
   `/tdd-implement` 啟動(那道鎖是「人審通過才實作」的唯一保證)。
