## 1. 四種使用者的設計思考（未來所有規劃都要帶這四個視角）

> 這張表是本工程的「需求羅盤」。每個工項動工前先對照：這改動服務誰？
> 動到他最在乎的東西了嗎？完工後此框架升級進 `ui-ux-guidelines.md`
> 並寫入 `/plan-feature` 模板（見工項 G1）。

### P1・訪客：來找服務的人

- **Why**：有具體需求（找某類服務、某個地區），想快速找到「可信」的
  提供者並取得聯繫。沒有帳號、沒有耐心，很可能從 LINE 分享連結進來。
- **最重要**：找得到（搜尋/篩選）、信得過（照片/地區/類別完整）、
  聯絡得上（詳情頁的聯繫資訊）。
- **必須正確**：刊登內容（聯絡方式、地區、服務範圍）——錯了就是白跑一趟。
- **必須穩定**：首頁與服務詳情頁——這是全站唯一「未登入也要完美」的路徑。
- **需要快**：首屏載入（第一印象），詳情頁開啟。**即時性要求低**：
  刊登更新分鐘級可見即可。
- **手機 vs 桌機**：壓倒性手機（LINE 內建瀏覽器），兩欄資訊卡瀑布；
  桌機是次要驗收情境。

### P2・刊登會員：花錢買曝光的人

- **Why**：付了訂閱費，要的是「我的服務有被看到」的證據與掌控感——
  刊登好不好編輯、狀態清不清楚，直接決定續訂意願。
- **最重要**：刊登流程順暢不掉資料（`multi-step-flow-recovery.md` 四契約
  已釘住）、刊登狀態一目了然（上架中／已隱藏——只有這兩種，由會籍有效與否即時推導，
  規格書 §11）、會籍到期日明確。
- **必須正確**：會籍/訂閱/付款狀態——這是金流，錯一次就是客訴。
  **含會籍失效狀態**（規格書 §5/§5.1 明訂的第三種角色狀態）：續約提示
  banner、刊登隱藏、「獎勵頁例外可讀」的呈現都要正確——這些畫面在
  色彩收斂與視覺對齊時是一級對象，不是邊緣分支（見 F2）。
- **必須穩定**：付款流程頁（PayUni 跳轉往返）。
- **需要即時**：付款結果回饋。**需要快**：會員中心開啟（已有 cache 層）。
- **手機 vs 桌機**：手機為主，長表單分步＋草稿保存（已有 `formDraft`）。

### P3・推薦會員：想額外賺獎勵的人

- **Why**：錢。獎勵數字、任務進度、提領狀態是他們每天回來看的理由——
  **數字錯一次，信任就沒了**。
- **最重要**：獎勵/點數/任務進度絕對正確、提領流程透明（現在到哪一步、
  預期多久）、推薦連結好分享（LINE 場景）。
- **必須正確**：所有金額與點數（規格書 §7–§10 是單一事實來源）。
- **必須穩定**：提領申請流程。
- **需要即時**：獎勵入帳、提領狀態變化。**需要快**：獎勵/任務儀表板
  （已有 stale-while-revalidate，模式正確、繼續沿用）。
- **手機 vs 桌機**：手機為主；分享動線與數字可讀性優先。

### P4・平台管理者：維持一切運轉的人

- **Why**：兩種模式並存——(a) **佇列處理**：提領審核、證件審核，講究
  批次效率；(b) **急救**：客服接到電話當下要能立刻查人、退件、停權
  （`WithdrawalManagement.tsx:167-169` 已釘住此原則）。
- **最重要**：審核判斷依據的資料**正確且完整**（看錯資料 = 做錯決定）、
  操作效率（每天重複幾十次的動作不能繞路）、危險動作有防線
  （`ui-ux-guidelines.md` §11 已釘住動作位階）。
- **必須正確**：會員狀態、提領金額、證件影像對應。
- **必須穩定**：審核的寫入操作（核可/退件/停權）。
- **需要即時**：系統告警、待審佇列數量。**需要快**：切換分頁不重新等待
  （見診斷 §2.5）。
- **手機 vs 桌機**：佇列處理以桌機為主；急救場景在手機——所以手機版
  不是「桌機縮小」，而是「急救動線」：查人、看狀態、一鍵處置要好按。

## 2. 七視角診斷（三個開發視角 × 四個使用者視角）

> 業主指出的六個問題不是個別 bug，是同一個病：**後台是功能逐個長出來的，
> 從沒有整體的資訊架構與設計語言**。以下按病灶歸納，每條附程式碼證據。

### 2.1 資訊架構（→ P4；業主問題 1、4）

- 五個頂層 Tab 中，「管理員設置」（`AdminSetup.tsx`）只顯示身分資訊——
  實際的授權操作在會員管理詳情面板裡。它存在的唯一理由是「系統尚無
  管理員時的 bootstrap」。
- ⚠️ **審查發現（P0-2）：bootstrap 的 GUI 路徑現況不可達**——
  `AdminRoute.tsx:24-26` 對非管理員一律導回 `/dashboard`，而「系統尚無
  管理員、可自助宣告」畫面正是給非管理員看的；journey 測試的 bootstrap
  是直接打 `/admin-setup/set-self-admin` API，不走瀏覽器。所以 A1 不是
  「搬移一個現行功能」，是要**先裁決這條路徑的去留與可達方式**（見 A1）。
- 五 Tab 在手機排成 3+2 兩列（`AdminDashboard.tsx:146` 的
  `grid-cols-3 md:grid-cols-5`），第二列兩格與第一列三格寬度不同，
  對齊破碎——業主指出的「換行醜」。
- ⚠️ **審查發現（P1-1）：移除第五 Tab 後「四 Tab 單列」不是自動成立**。
  按 `AdminDashboard.tsx:118-152` 既有的真瀏覽器量測法：375px 下 track
  337px，四欄每欄 84.25px、扣內距剩約 66px 可放文字，而最長標籤
  「獎金提領管理」實測需 84px——會 ink overflow。**單列的前提是縮短
  標籤**（提案：「提領／會員／公告／告警」，二字標籤綽綽有餘），
  S3 必須以同一套量測法＋`test_admin_tab_labels_do_not_ink_overflow`
  驗證；驗證不過的退路是維持兩列但改為 2+2 等寬。

### 2.2 版面與控制列（→ P4；業主問題 2）

- 「狀態篩選、重新整理、下載CSV」（`WithdrawalManagement.tsx:704-738`）
  用 `flex-wrap` 任其換行，手機上三件東西擠成兩行、斷點附近忽一行忽兩行。
  病因：三個控制項平鋪，沒有按「使用頻率 × 螢幕預算」分配位置
  （§11.2 視覺權重原則的同類問題,但發生在工具列而非列動作）。

### 2.3 詳情面板設計（→ P4；業主問題 3）

- 會員詳情（`MemberManagement.tsx:274-405`）是一條從頭到尾的扁平 `dl`
  清單：身分、會籍、金流、推薦關係、敏感資料、提領記錄、管理動作全部
  同一視覺層級擠在一個 Sheet 裡。P4 在審核時要的是「先知道這是誰、
  狀態如何，再往下找細節」，現在是「從第一行讀到最後一行」。
  動作位階（§11.1）當初做對了（人的狀態變更收在詳情裡），但**資訊
  本身沒有位階**。

### 2.4 設計語言（→ 全部 P；業主問題 6）

- Token 主色 `--primary: #030213`（`globals.css:15`）與 logo 的黑白極簡
  一致——**方向本來就對，但沒人守門**，大量頁面繞過 token 手刻：
  - `MemberManagement.tsx:418-465` 統計數字直接 `text-blue-600` /
    `text-red-600` / `text-green-600`；
  - `AdminSetup.tsx` 四色提示框手刻 `bg-gray-50/green-50/blue-50/yellow-50`；
  - 漸層四處各唱各的調：`task/ProgressBar.tsx`（blue→purple）、
    `TaskDashboard.tsx`（orange→yellow）、`task/PendingRewardsSection.tsx`
    （yellow→orange）、`PaymentResult.tsx:540`（green→blue）；
  - 狀態 Badge 手刻 class string（`MemberManagement.tsx:53-54`），
    不走 `ui/badge.tsx` variant。
- 病因與本 repo 已付過學費的教訓同構：**沒有機械把關的規範必然漂移**
  （文件命名、規格漂移都是先亂後立 checker 才守住的）。所以解法不只是
  「改一輪顏色」，而是 token 收斂 ＋ **新增色彩使用檢查腳本**進 CI。

### 2.5 感知效能（→ P4 為主、P1 次之；業主問題 5）

- **「loading 差一點點」的真兇是架構性的**：Radix Tabs 非 active 分頁
  不掛載 DOM（`AdminDashboard.tsx`），好處是首進不會五路 API 齊發，
  代價是**每次切回一個分頁，元件重新掛載、state 歸零、重新 fetch、
  重新看一次 loading**。P4 在提領↔會員之間來回切是日常動線，每切一次
  等一次。前台會員區早已用 `DataCacheContext` 的 stale-while-revalidate
  解掉同型問題（切回來瞬間顯示舊資料＋背景刷新）——**admin 缺的就是
  這一層**，把成熟模式延伸過去即可，不需要發明新東西。符合業主
  「穩定是最大訴求」：不動請求時序、不做激進預載，只是不丟棄已載資料。
- Loading 呈現不統一：`MemberManagement` 用 `Skeleton`（✅ §5 規範），
  `AdminSetup` 用置中 spinner（❌），前台 `ServiceProviderDetail.tsx:39-64`
  用純文字「載入中...」（❌，且它在 P1 的關鍵路徑上）。

### 2.6 需求視角總結（plan-reviewer-requirements 溯源點）

- 本工程**不改任何業務規則**：會籍/獎勵/任務/提領的規則、金額、狀態機
  一律不動（規格書 §7–§10 不變）。所有改動是呈現層與資料快取層。
  唯一的行為變更是 §2.1 的 AdminSetup Tab 移除與 bootstrap 可達性裁決
  （見 A1）。規格書 §13 需**人工**同 PR 更新——審查已查證
  `check-spec-drift.py` 抓不到 §13 元件表的裸元件名，**沒有機械把關**，
  S3 必須逐處修：§13 模組表的 AdminSetup 列
  （`uknow-software-specification.md:625`）、§13.1「釘死的 5 欄 grid」句
  （同檔 :673）、`AdminDashboard.tsx:109-110` 與 `App.tsx:71` 的
  同措辭註解。

### 2.7 架構視角總結（plan-reviewer-architecture 溯源點）

- 全部改動落在 `src/`，不動 `supabase/functions/`（API 契約零變更；
  admin cache 只是前端讀取層）。
- 既有成熟模式優先於發明：`DataCacheContext`、`useMediaQuery` 擇一渲染、
  `Skeleton`、`usePagedList`、Badge variant——本工程是**把成熟模式推廣
  到落後區域**，不是重寫。

## 4. 設計語言規範方向（黑白極簡，D1 的草案）

1. **基底不變**：`--primary: #030213`（近黑）與 logo 相符，保留。
   根字級/觸控目標/表單規範（§1）全部不動。
2. **灰階做層次**：資訊層級靠字重、字級、`--muted-foreground` 灰階與
   留白表達，不靠顏色——這是 logo 的語言。
3. **語義色是唯一的彩色**，且只綁狀態語義：
   - 成功/已完成 → `--success`（新 token，收斂現有各種 green）
   - 警示/待處理 → `--warning`（新 token，收斂 yellow/orange）
   - 危險/失敗 → `--destructive`（已有）
   - 資訊/進行中 → 灰階或 `--primary`，**不再用藍色**（藍是目前漂移
     最兇的方向）
4. **漸層退場**：裝飾性漸層（任務/獎勵/進度條四處）一律改為單色或
   灰階；「活力感」由留白、圓角、微陰影與動效層次提供，不由彩色提供。
5. **統計數字**（admin 卡片、儀表板）：數字一律 `--foreground` 黑，
   語義由旁邊的標籤/圖示承擔——數字本身不上色（色盲友善，也符合極簡）。
   判準補充：**非狀態語義的計數**（總會員數、管理員人數這類）一律去色
   走純黑；只有明確落在四類語義（成功/警示/危險/資訊）的狀態呈現才上色
   ——這條是給 S2 機械替換時的裁決依據，不留各自詮釋空間。
6. 深色模式維持既有 token 結構（`.dark` 的層次規則 §2 不變），語義色
   同步補深色版本。⚠️ 現況 `.dark` 從未被實際套用（無切換入口、無任何
   import），深色 token 沒有驗證管道——D1 交付物須含**驗證 checklist**
   （devtools 手動在 `<html>` 掛 `.dark` class 逐頁目視），否則深色版
   只是紙面正確。

7. **強調色（2026-10-03 追加，業主裁決 A）**：全站唯一的強調色（非語義）是 `--brand`（靛藍），**只表示「可以互動／正在看這裡」**，不表示任何狀態——所以它與第 3 點「資訊/進行中不用藍」不衝突：資訊狀態仍走灰階，靛藍只出現在連結、選中分頁、進度填色、焦點框、次要行動鈕。主按鈕維持 `--primary` 黑。同時語義色的實心層（A 形狀）改為**亮底黑字**（`#22c55e`／`#fbbf24`／`#f87171` 配近黑字）：亮色配黑字的對比（7–12:1）反而高於深色配白字（5:1），等於在同一道 WCAG 門檻下換到鮮得多的顏色；淺底 B 形狀與裸字 C 形狀不動。

8. **推薦樹的世代色（2026-10-03，業主裁決，同日改向）**：第 5 點 (c)「多值分類色一律去色」維持，但推薦樹的世代是該頁的主要閱讀鍵，核准三個專用色相（一代 teal、二代 violet、三代 pink）作為**唯一例外**。條件：避開語義色與 brand 靛藍的家族（二代 violet 與 brand 最接近，但只用在頭像圓形上，不會被讀成可互動）、結構同時由縮排承擔、不得擴散到其他頁面。版面維持 S2 之後的原樣——頭像＝世代、右下角小點＝訂閱狀態，各占一個視覺編碼面。（同日稍早的裁決「顏色從世代搬到訂閱狀態」已撤回：看過預覽後業主認為推薦樹原本就沒有這些狀態呈現，不需要多出狀態 chip、整列淡黃、右側狀態文字與「新」tag。）

9. **顏色分工（2026-10-04～05 定案，取代第 7 點的「靛藍」）**：
   - **墨色**（文字 `#121223`、灰字 `#646478`、邊框 `#e3e4ee`）＝文字、邊框、**可互動**（圖示、chevron、連結底線、FAB 圖示）與**流程主要動作鈕**——石板墨互動色已放棄，與文字墨黑合併，不另設互動色；流程鈕就是 main 現行 `Button` default（`--primary` 底白字、hover 90%、深色反白）。
   - **品牌色＝蔚藍 Ocean**（50 `#ecf8fd`／100 `#cfeefb`／300 `#519cc3`／600 `#0369a1`／800 `#0c3d5c`；深色 600 `#4cc3f0`、淡底 `#0b2f44`、淡底字 `#a8e0f7`），只出現在兩處：**引導鈕**（續訂 ＞ 加入推薦計畫 ＞ 確認收款，一頁一顆）與**重點與進度淡底**（每頁一塊主區淡底、推薦總人數卡、任務獎盃底、任務徽章填色）。選中分頁／連結／焦點框不再用品牌色。
   - **選取與聚焦一條規則**：一個顏色＝灰字（墨色 600，`--muted-foreground`，token `--sel`）；一個訊號＝有邊框的元件（輸入格、縮圖、方案卡、OTP 目前格）框線變灰字單圈 2px，沒邊框的元件（chip、分段切換、分頁格）底色灰字、文字反白；不疊加勾號、淡環、粗體、底色（方案框選中已有外框就不加勾）。只有「值」不適用：勾選框打勾＝`--primary`、底部導覽目前頁＝墨黑（休息態已是灰字）。鍵盤 `focus-visible` 例外保留 3px 環（瀏覽器自動只在鍵盤操作時顯示），**全不透明 `--sel`**——2026-10-05 業主在 #354 裁決 D1 取代原本的「淡環」：30% 透明對白底 1.54:1，過不了 WCAG 1.4.11，S2b「焦點環全不透明」維持；輸入格類聚焦仍是框線變灰字單圈 2px，不疊環。
   - **語義色**維持三類與 A／B／C 三形狀，值換成新色表（見第 12 點）。世代三色 teal／violet／pink 維持，擴散到所有提到「代」的地方（chip、小圓點、頭像），與蔚藍只靠形狀分開。
10. **按鈕三分法（2026-10-04 定案）**：
   - **主動引導**＝實心、容器色，黑白卡片用品牌色；只含續訂（會籍失效；30 天內到期的提前續訂暫藏，見 progress 遺留事項）＞ 加入推薦計畫 ＞ 確認收款，一頁一顆。
   - **流程主要動作（不做就中斷）**＝實心、容器色，黑白卡片用墨黑（`Button` default）：繼續／登入／註冊／下一步／前往付款／建立刊登／儲存變更／提交申請／確認領取／確認查收；後台的通過、標記已匯款、確認匯款、發布公告、設為管理員。
   - **次要動作**＝白底、容器色外框與字（黑白卡片＝灰框墨字）：申請提領、立即刊登、領取獎勵、分享邀請、查看、編輯、上一步、取消；流程的起點也算次要。破壞性＝紅框字，不可逆的確認框裡才紅實心。
   - **位置與大小只看容器與裝置，與主次無關**：手機表單與卡片尾整寬堆疊、兩顆並排等寬次要左主要右、提示框內靠右文字寬、列內同行靠右較矮、觸控 44px；桌機表單靠左對齊欄位（最小 120px）、對話框與卡片尾靠右次要在左、四欄狀態小卡整寬。
