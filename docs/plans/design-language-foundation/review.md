## 發現清單（依嚴重度排序）

### P1（實質缺口，實作前應補）

**P1-1〔§2.4 C1 掃描規則〕色值的非 class 表達形式是掃描盲點（系統＋UIUX，合併）**
C1 只比對 Tailwind 具名調色盤 class，抓不到兩類等價寫法：
(a) **JS/TS 內的原始 hex 字面值**——`ReferralTreeView.tsx:83-90` 的 `GEN_AVATAR`
（`#16a34a` / `#7c3aed` / `#ea580c`）經 `style={{ backgroundColor }}` 套用、
`inviteCardImage.ts` 的 canvas `ctx.fillStyle`；全 repo 共 14 處、5 個檔案（已核實）。
(b) **Tailwind 任意值語法**（`bg-[#16a34a]`、`text-[rgb(...)]`）——現況 0 處（已核實），
但規劃刻意不給行內豁免、baseline 也不收新項，這恰好讓任意值成為壓力下最方便
且完全不被監視的逃逸路徑。
§2.2 據此斷言「全 repo 掃不到任何品牌色…沒有任何一處是真的不能 token 化」，
這個「baseline 完整」的前提與實測不符。
→ C1 補一條原始色值偵測規則（至少涵蓋 `'#rrggbb'` 字面值與任意值語法），
階段 3 自測表格各補一案；或在 §2.2 明列此盲點與「暫不管」的理由，
不要用「掃不到」帶過「沒去查這個維度」。

**P1-2〔§2.1 token 表／§5 階段 2〕border token 用錯對比門檻（UIUX）**
`--success-border` / `--warning-border`（及 Q1 若通過的 destructive border）
是**非文字元素**，正確門檻是 WCAG 1.4.11 的 **3:1**（對相鄰背景），
不是文字用的 1.4.3 / 4.5:1。目前階段 2 的驗收標準只寫兩組文字配對，
border token 完全沒被驗到——可能過關卻對比不足到肉眼分不出邊框。
→ 補「`*-border` 對其相鄰 `*-subtle` 背景（淺/深各自）≥ 3:1」，
並在 §12 新章節明文區分「文字 4.5:1／非文字·邊框·icon 3:1」兩種門檻。

**P1-3〔§2.1 token 表／§4.2〕裸文字·裸圖示沒有 token 對應規則（UIUX）**
現況大量存在第三種形狀：文字/圖示**直接疊在頁面或卡片底色上、無 bg/border 包裹**
（`TaskDashboard.tsx:103` 的 `text-red-600` 錯誤訊息、`ThreeStepDialog.tsx:308,333`、
`MemberVerifyQrTab.tsx:46`）。S2 該對應 `--success`（為實心底設計的飽和色）
還是 `--success-subtle-foreground`（為淺底文字設計、對比已驗證）？兩者對白底的
對比表現不同，規劃完全沒定義。
→ §2.1／§4.2 補第三種對應規則，並排進階段 2 的對比度測試矩陣。

**P1-4〔§4.2 第 3 點／Q4〕藍色退場後的色盲可用性未評估（UIUX）**
拿掉 `--info` 後僅剩綠/黃橙/紅，其中**紅綠正是紅綠色盲最難區分的組合**
（deuteranopia/protanopia 約占男性 8%），而藍恰是原三色系裡與紅、綠都不混淆的色相。
規劃沒排任何色盲模擬驗證，也沒把 WCAG 1.4.1「狀態不可只靠色相辨識，
需搭配文字/圖示」寫進新章節。Q4 自己承認這是「視覺上最劇烈的單一改動」，
卻沒評估它對可用性的後果。
→ §4.2／§4.3 補色盲模擬驗證項目（devtools vision-deficiency），
並明文要求新狀態呈現不得只靠色相傳遞語意。

**P1-5〔§4.2 第 5 點〕非狀態三類判準涵蓋不到「多值分類色」（UIUX）**
`ReferralTreeView.tsx:49-58,83-90` 用綠/紫/橘標示**推薦樹世代**（一代/二代/三代），
該檔註解明言這條色彩軸是刻意與訂閱狀態色分開設計。它勉強落入 (b) 身分/分類標記，
性質上卻更接近 `--chart-*` 的多值分類色用途——而 `--chart-*` 已被 §1.4 scope out。
兩種讀法都說得通，S2 會卡住；這與上游 §4 第 5 點「不留各自詮釋空間」正面衝突。
→ 補一條明確案例裁決：世代色歸 (b) 去色，或改用 `--chart-*`，擇一並說明理由。

**P1-6〔§2.1／§2.4／§7〕灰階在掃描範圍內，但 token 分層表沒有灰階對照表（系統）**
§7 明文「C1 用 Tailwind 官方 22 色全表，不挑選」——官方 22 色含灰階家族
（slate/gray/zinc/neutral/stone），已核實現況 **39 處、15 個檔案**
（`PaymentResult.tsx` 17 處最多、`gender.ts`、`ThreeStepDialog.tsx` 等）會落入
C1 並算進 baseline。但 §2.1 的 token 分層表只覆蓋彩色語義色，**灰階收斂無表可查**，
且非 1:1 替換（既有 `--muted-foreground: #717182`、`--border: rgba(0,0,0,0.1)`
未必與各處 `gray-400`/`gray-200` 視覺吻合，貿然替換有視覺回歸風險）。
這正是「S2 收斂到一半發現缺 token」的具體寫照。
→ §4.2 比照 §2.1 補一張灰階對照表，或明確裁決灰階不在 C1 範圍內並說明
為何這不算「挑選」——兩者擇一，但不能沒有交代。

**P1-7〔§2.2 三處同步／§5 階段 1〕`@theme inline` 只驗 key 存在、沒驗指向（系統）**
階段 1 只斷言 token 在三處「存在」。複製貼上打錯一個字
（`--color-success-subtle: var(--success);` 漏改成互指）不會被抓到——
這正是本節自己點名的「靜默失效」同一類問題，但驗證只堵了「漏一處」這一半，
沒堵「指錯一處」。
→ 測試改為比對 `@theme inline` 每一行的**值字面**等於預期的 `var(--token名)`。

**P1-8〔§2.3／§5 階段 2／Q1〕既有 `.dark --destructive` 是 oklch，會撞上自陳規則（系統）**
`globals.css:64` 的 `.dark { --destructive: oklch(0.396 0.141 25.723); }`（已核實）。
Q1 若採納「補 destructive 三件組」並比照 success/warning 把 destructive 全家族
（含既有 solid/foreground pair）納入對比度測試，會直接撞上 §7 自陳的
「讀不到可解析色值就直接紅，不靜默跳過」。規劃沒交代既有 pair 要不要納入、
要不要順手把 `.dark` 的 destructive 改成 hex。
→ 此決定必須在階段 2 動工前定，併入 Q1 的裁決一起說明。

**P1-9〔§3.1／`progress.md:3-6`〕plans-keep 標記與 friction-log 2026-09-02 明文判定相牴觸（架構）**
`progress.md` 用 `<!-- plans-keep: ...施工鷹架... -->` 自我豁免
`check-plans-scaffold.py`。但 `friction-log.md` 2026-09-02 條已明文判定這正是
**不該用**的用法：「豁免標記的語意是『這份**不是**施工鷹架』，施工中的鷹架正是
它要擋的東西。**用它等於說謊**」，並把真正的修法留給整併時改判準
（看 draft PR／`progress.md` 是否全綠／分支有無產品 commit，而非「有沒有標記」）
——該修法至今未做（`has_keep_marker()` 仍只檢查字串存在）。
同一模式已在上游 `platform-uiux-redesign/progress.md:3` 出現過一次，
所以不是本規劃獨創，但也沒有任何地方寫下「為什麼這次沿用它」。
機械上 framework-check 會綠，但長期後果是這個標記變成任何三段式 feature 都能貼的
萬用通行證，稀釋掉 `upline-pairing-lines/rules.md` 那種真正永久居留的信號
（`check-plans-scaffold.py` 檔頭自己講的設計重點正是要防這件事）。
→ 要嘛明文記錄「已知與 friction-log 衝突，本次沿用因為 X」並排入下次框架整併，
要嘛照 friction-log 記錄的處置走（收尾前不 push、commit 壓在本機湊批再推）。
不要讓標記靜默通過。

### P2（建議，不改也能正確交付）

**P2-1〔§2.4 C2〕漸層盤點漏 4 處，且漏掉的是判準涵蓋不到的第三類（架構）**
C2 清單寫 9 處／5 檔，實測 **13 處／6 檔**（已核實）——漏掉
`src/utils/userReferralFormatter.ts` 的 `getProgressBarStyle()` 4 處。
諷刺的是那正是 §2.4 開頭引用來說明「色不只住在 JSX 裡」的同一個檔案
（當時只看了 `getProgressColor`）。更重要的是這 4 處是**依進度百分比切換的
狀態式漸層**，既非純裝飾也非文字可讀性遮罩，§4.2 第 4 點的兩類判準套不上。
→ 重新完整掃描（別讓手抄數字進文件），並補「狀態驅動的連續漸層」這一類判準
（例如：改用離散語義 token 分段對應）。

**P2-2〔§2.4 baseline〕孤兒條目沒有反向檢查（系統）**
三條判定都以「掃到的檔案」為準，不檢查 baseline 裡的路徑是否仍存在。
檔案刪除後條目殘留；日後若有無關新檔恰好重用同一路徑，會被誤判為「已在 baseline 內」
而放行（洩漏上限為舊條目的數字，有界但實質繞過了第一條規則的精神）。
→ 掃描時驗證每個 key 對應檔案存在，孤兒項列印並紅（比照「低於 baseline 要收緊」的精神），
階段 3 自測補案。

**P2-3〔§2.4 baseline〕rename 全紅是刻意嚴格，但沒寫進「怎麼用」（系統）**
檔案 rename 後舊 key 失聯、新路徑被當「不在 baseline 的新檔」而全紅——這是刻意
（逼 rename 與 baseline 更新同一個 PR），不是漏洞，但沒寫明會讓第一次撞到的
session 誤以為是 bug 去 debug。
→ §4.2「守門腳本怎麼用」補一句：rename 時 baseline key 要一併改名。

**P2-4〔§2.4 C2〕漸層「功能性 vs 裝飾」判準不可操作（UIUX）**
`ProgressBar.tsx:54`（標題疊在 `from-blue-50 to-purple-50`）、
`TaskDashboard.tsx:195`（獎勵文字疊在 `from-yellow-50 to-orange-50`）這類中間案例，
「文字疊在漸層上」為真但拿掉漸層依然可讀，實質是裝飾——現行判準全靠語感。
→ 補可操作步驟：拿掉漸層換等亮度純色，文字對比度是否仍達標；
仍達標＝裝飾可退場，不達標＝功能性。

**P2-5〔§4.2 節標題〕「上游 §4 七點」實際只有六點（UIUX）**
上游 `plan.md` §4 只列 1–6；本規劃的第 7 點「守門腳本怎麼用」是新增內容。
§1.1 強調「每個斷言都標了依據」，這處標題與依據對不上。
→ 改標題措辭，明確區分「上游六點」與「本規劃新增第 7 點」。

**P2-6〔§2.5／§3.1〕baseline.json 是 checker 家族第一個外部資料檔，未交代選址（架構）**
現有九支 framework-check checker 與 `check-bundle-budget.mjs` 的判準常數**全部內嵌**
在腳本本身；唯一的執行期資料檔（`harness-metrics.py` 讀的 jsonl）放在 `.claude/`
而非 `scripts/`。放 `scripts/` 不是不行，但這是對既有形狀的結構性偏離，
§3.1 直接列為新增、無說明。
→ 補一句選址理由，或考慮 `scripts/data/` 子目錄以維持 `scripts/` 可執行檔的清爽度。

**P2-7〔§2.4 baseline 粒度〕C1／C2 合併計數，一增一減會靜默通過（架構）**

→ 階段 3 明確決定要不要拆成 `{path: {c1: n, c2: m}}`，別留到 S2 才發現。

**P2-8〔§2.4／§1.1〕未明文承認對上游「白名單機制」字面的偏離（需求）**

**P2-9〔§6〕Q2／Q5 已實質定案，不該與 Q1／Q4 混在同一張清單（需求）**

## 發現清單

**[P1] R2-系統-1〔§2.3／§5 階段 2〕P1-8 只轉了半個 token pair**
`.dark` 底下 `--destructive`（`globals.css:64`）與 `--destructive-foreground`
（`globals.css:66`，`oklch(0.985 0 0)`）**兩者都是 oklch**，修訂 2 只處理前者。
但 §2.3 自己寫「destructive **全家族**進對比度測試」，而 §2.1 的 A 組配對
正是這一對——自己診斷出的問題只解了一半，另一半會在完全相同的位置再卡一次。
→ **已回填**：§2.3 改為表格列出兩個 token；階段 2 標題同步。

**[P1] R2-UIUX-1〔§4.2 第 5 點 (c)〕世代灰與「已失效」灰的碰撞未被評估**
推薦樹同一畫面上已有另一套灰：`ReferralTreeView.tsx:72` 的
`expired: { dot: 'bg-gray-400', label: '已失效', badge: 'bg-muted text-muted-foreground' }`
——那裡的灰是「已失效」的專屬語意，不是「沒有顏色」。
把世代頭像也去色成灰階三階，三代且已失效的節點會變成「頭像灰＋狀態點灰＋
badge 灰字」三重堆疊，稀釋掉負面訊號。而該檔 `:84` 的註解明言
「先前是 userId 雜湊色，調色盤與狀態色／世代色撞色，容易被誤讀成分類」
——**避免世代色與狀態色互撞本來就是這個元件既有的設計目標**，裁決正好與它反向。
規劃全文未出現「已失效」三字，代表這個互動完全沒被檢視過。
→ **已回填**：§4.2 第 5 點 (c) 加碰撞防呆（與 `--muted-foreground`/`gray-400`
保持可辨識亮度差距）＋ S2 驗收站 1 明列「深色模式下世代頭像灰是否與已失效圓點灰混淆」。

**[P1] R2-架構-1〔§5 階段 5〕灰階對照表的「涵蓋 39 處」沒有測試落點**
階段 5 的驗收標準可數可枚舉，但同格測試落點只有 `check-document-naming.py`
與 `check-context-budget.py`——前者查檔名、後者查 token 預算，**都不驗表格內容**。
這正是本規劃在 P1-7、P1-2 親自點名的「宣稱驗過但沒驗到」失效模式，
只是這次發生在文件而非程式碼。`check-spec-drift.py` 已立下「列舉與文件不一致就紅」的先例。
→ **已回填**（業主裁決：機械化）：§2.4 新增 **G1 段**——掃到的每個灰階 class
都必須在 §12 對照表有對應列，缺列即紅；階段 5 的測試落點改為 G1。

**[P2] R2-系統-2〔§5 階段 3〕C3 自測表格缺 3 位數簡寫案例**
自測案例全用 6 位 hex（`#16a34a`）示範，但實測 14 處裡有一個是 3 位簡寫
（`SignaturePad.tsx:60` 的 `'#000'`）。implementer 依樣只寫 `#[0-9a-fA-F]{6}`
就會漏檢，與規劃聲稱的 14 處對不上——D2 自己最在意的「靜默失效」同一類。
→ **已回填**：階段 3 表格補 true-positive 案例。

**[P2] R2-需求-1〔§2.4 C3(a)／§5 階段 3〕C3 缺假陽性防呆案例**
非色彩用途的 hex-like 字串（`href="#a1b2c3"` 錨點、hash 片段）可能被誤判為色值。
規劃刻意不設行內豁免，**一旦誤收進 baseline 就排不掉**，只能靠日後 rename
觸發全紅才會被注意到。現況 14 處實測全是真色彩用途，此為防未來。
→ **已回填**：階段 3 表格補 true-negative 案例；§7 風險表補一列。

**[P2] R2-UIUX-2〔§4.3〕色盲 checklist 被定位成 S2 的一次性驗收工具**
「即使完全分不出顏色，狀態仍然讀得懂」這條標準本身可操作，但 §4.3 末段寫
「它是 S2 的驗收工具」，代表 S2 之後任何新增的純色狀態呈現都沒有防線
——WCAG 1.4.1 會退化成「大家記得的話」。C1–C3 是語法層規則，
抓不到「這個 badge 是否只靠顏色傳遞語意」（技術限制，非規劃疏漏）。
→ **已回填**：§4.3 改為常設規範，§12 措辭定為「任何新增或修改狀態視覺呈現時都要跑」。

**[P2] R2-架構-2〔§5／上游 construction-plan §2〕S1 增重未觸發計畫異動機制**

「每個 session 的範圍都小到 Sonnet 能穩定完成」，而 `construction-plan.md` §4.4
自己要求「計畫要改就要在 `progress.md` 記一行異動」——這次沒觸發。

`construction-plan.md` 的 S1 重量標註同步。
