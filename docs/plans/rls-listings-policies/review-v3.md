## 三輪都在追、本輪確認關閉的重點

- **`relrowsecurity` 斷言寫法**(系統):`'public.listings'::regclass` 轉型與
  `withdrawals.test.ts:553-558` 既有模式一致;第 2–6 條全是 metadata 查詢、
  不受 RLS 影響,所以第 1 條確實是唯一能抓到「RLS 被關掉」的斷言。
  **`relforcerowsecurity` 不需一併釘**——它只影響 table owner;`anon`/`authenticated`
  從來不是 owner,`service_role` 繞過靠角色的 `BYPASSRLS` 屬性,本案威脅模型裡
  沒有角色會被它影響。
- **空白正規化比對**(系統):`pg_get_expr` 輸出的是運算式**樹**的反編譯,任何
  「條件被改寬」必然改變 token,不會只停在空白層級——**沒有假陰性風險**;
  殘餘的跨版本結構差異只會造成**誤報(fail loud)**而非**漏報**,加上失敗訊息帶
  `version()`,是把無法在規劃期消除的風險轉成可診斷的失敗。
- **§0 三段論證**(系統 + 需求):`has_active_subscription()` 是
  `(未過期) AND (未停權)` 的合取且為 `security definer`,RLS 只吃最終布林值、
  不區分哪一支使假——所以用 expired 分支證明機制、用既有單元測試證明 suspended
  分支的函式輸出、用 L1 golden 綁定兩者,三段疊加確實推得出結論。**未發現第四個
  未言明的前提。**(「沒有其他 permissive policy 覆蓋掉結論」由 L1 第 2 條獨立守住。)
- **`pytest_expr` 四段推理鏈**(系統 + 架構,各自獨立驗證):`journey.yml:331-332`
  的 `-m` 組法、`10_org_build.feature` 只標 `@journey @orgbuild`、
  `conftest.py:27-34` 的 `pytest.skip`、`MIN_FILTERED=1` 的 `ran=0 < 1` 硬失敗
  ——四段全部與程式碼實況吻合。
- **四階段切分不必拆**(架構):characterization 測試在一個檔案裡放多條
  `Deno.test` 屬本 repo 常態(`withdrawals.test.ts`、`name-write-paths.test.ts`
  同形),第二輪已用同一理由拒絕拆分,本輪未找到推翻它的新證據。
- **`rest_as_user.py` 無測試檔站得住**(架構):`check-test-names.py` 全文只掃
  `src/**/*.test.ts*`、`supabase/functions/api/*.test.ts`、`e2e/features/*.feature`、
  `e2e/journey/features/*.feature` 四個路徑,**完全不掃 `e2e/journey/tools/`**;
  `supa.py` 是既有同形先例。
- **`feature-plan-guard.py` 不會擋 §9 的 `src/**` 寫入**(架構):`plan_ever_existed()`
  同時查工作目錄與 `git log`,規劃檔在整個實作期都在分支上。
- **情境數 38 → 49 與 marker 清單**(架構獨立重算):9 個既有 feature 共 38 條,
  +11 = 49;`pytest.ini` 現有 10 個 marker,`rls` 確實尚未登記。
  B5/B6/B7 只出現在 `orgchart.yaml`,`e2e/journey/` 其餘零匹配。
