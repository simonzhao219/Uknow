## 輸出契約(reviewer 必讀)

**審查對象**:呼叫方會指明是「規劃」還是「實作 diff」,並給檔案路徑
**或**直接把內容放在 prompt 裡(輕量改動走 Plan Mode 時不落檔,你看到的
就是全文——照樣審,不要因為沒有檔案路徑就要求對方補)。
- 審**規劃**(`/review-plan`):看設計是否正確、完整、可實作
- 審**實作 diff**(`/review-implementation`):除了你本身的視角,**必問一題
  ——實作有沒有偏離 plan?** 偏離未記錄在 PR「偏離規劃說明」的,一律至少
  P1。規劃審過、實作走偏是最常見的失敗模式,這一關專門攔它

**嚴重度定義**:
- **P0(阻擋)**:照此規劃實作會做錯功能、壞既有行為、或造成資料/資安事故
- **P1(應改)**:規劃有實質缺口,實作前應補——不補則實作期必然撞牆
- **P2(建議)**:有更好的做法,不改也能正確交付

**每項發現的格式**:`[P?]〔規劃書章節〕缺口一句話 → 建議一句話`

**逃生口(合格產出的一部分)**:
- 某面向檢視後無缺口 → 明確寫「無缺口」,**禁止為交差發明問題**
- 不確定是否為真問題 → 標「〔需人工裁決〕」,不要自行定性
- 只報缺口,不報風格偏好

**聚合規則(主 session 必讀)**:只彙整、去重、排序,**不改判**——severity
以 reviewer 原判為準;要降級或剔除任何發現,必須列入「需人工裁決」並附理由。

## 發現清單(依嚴重度排序)

### P0

`[P0]〔2. 系統設計〕`「不加 DB constraint」的決定未查證 `profiles` 表既有
寫入路徑——`20260620000009_auth_profile_hardening.sql` 已對 `authenticated`
角色開放 `name`/`phone`/`birth_date`/`national_id`/`bank_code`/`bank_account`
的直接 UPDATE GRANT,搭配 RLS `profiles_update_own`(`id = auth.uid()`,
`20260620000002_rls_policies.sql`),任何登入用戶可直接打
`PATCH /rest/v1/profiles` 寫入任意姓名,完全繞過規劃唯一的防線
(`POST /auth/register`、`PUT /auth/profile` 兩個 Edge Function 端點)。
`profiles` 表上僅有的 BEFORE UPDATE trigger(`trg_profiles_updated`、
`trg_profiles_no_escalation`)都不管姓名格式。規劃自陳的核心動機之一
(擋掉「任何持有效 token 的使用者直接打 API 把姓名改成任意字串」)照此規劃
實作後依然成立,只是換一個不需要理解 Edge Function 契約、更直接的路徑
→ 三選一裁決:①撤銷 `name` 欄位的直寫 GRANT,逼所有寫入走
service_role(Edge Function);②比照既有 `trg_profiles_no_escalation`
(`20260620000003_functions_and_views.sql:75-77`)前例,加 BEFORE UPDATE
trigger 或 CHECK constraint 做最後防線;③在規劃風險章節明文接受此殘留
繞過面並寫明理由。不要用「決定不加」的篤定語氣掩蓋一個其實查得到答案的
技術事實。
*(系統視角原判 P1、建議同樣的三選一;需求視角原判 P0,認為規劃如實作
將無法達成自陳的核心防線目的。兩者是同一缺口的獨立發現,severity 判斷
不同,予以如實保留,兩份原始論證都成立,如何裁決留給人工。)*

### P1

`[P1]〔3. 架構影響〕`規劃新增的姓名格式驗證函式未提及重用
`maskNameByGen` 正上方既有的 `HAS_HAN`/`HAN_RANGE` 正則
(`supabase/functions/api/index.ts:2380-2382`,範圍
`㐀-鿿`+`豈-﫿`)——該正則的註解記載過一次真實事故
(NFC 正規化誤判導致 emoji 姓名觸發 500)。若新函式獨立重寫判斷邏輯:
一是可能重蹈同一 Unicode 邊界陷阱;二是可能與 `maskNameByGen` 對「什麼算
中文姓名」的認定不一致,導致「通過驗證的姓名,遮罩卻仍顯示英數樣式」,
原地重現這次問題的觸發症狀本身(推薦網絡頁看到英數風格遮罩名)→ 新函式
明確重用或至少匯出/對齊 `HAS_HAN`/`HAN_RANGE`,並加測試釘住「通過
`validateName` 的姓名,`maskNameByGen(gen=2)` 必為中文遮罩樣式」。
*(UI/UX、架構、需求三個視角各自獨立發現同一缺口,一致判 P1——三次獨立
命中同一段程式碼,信心度高。)*

`[P1]〔2. 系統設計〕``PUT /auth/profile` 是逐欄位局部更新端點(現況只在
`jsKey in body` 時才寫入該欄位),規劃未言明新姓名驗證應「只在 body 含
`name` 時觸發」——若對 `body.name` 做無條件格式檢查,日後任何只改手機/
銀行帳號的局部更新請求會被誤擋、或對 `undefined` 呼叫字串方法而回 500
→ 階段 2 驗收標準需明確加入「不含 `name` 欄位的 `PUT /auth/profile`
請求維持既有局部更新行為」的情境與測試。*(系統視角)*

`[P1]〔5. 階段切分〕`Phase 2 一方面承諾姓名驗證函式的「純函式部分」由
`*.unit.test.ts` 直接覆蓋,另一方面把放置慣例對標 `maskNameByGen`/
`verifyNationalId`——但這兩者在 `index.ts` 中都未 `export`,現有慣例下
只能透過 HTTP 整合測試間接測到;真正能被 `.unit.test.ts` 直接 import 的
既有前例(`resolvePayuniConfig`、`generateTradeNo`)都是 `export
function`。規劃兩處引用的「既有慣例」互相矛盾 → 明確寫出新函式需
`export`(比照 `resolvePayuniConfig`),否則實作者 Phase 2 開工時會當場
撞上這個未解決的分歧。*(架構視角)*

`[P1]〔6. 開放問題#1〕`規則嚴格度討論只泛稱「少數合法登記姓名含羅馬拼音」,
未點名台灣原住民族依《姓名條例》擁有以羅馬拼音單獨登記法定姓名的權利——
這是整個族群的法定命名權,不是零星邊緣個案。若規則最終採「至少含一個中文
字元」,需為純羅馬拼音合法姓名設計不被擋下的路徑,否則規則上線後會系統性
排除該族群完成註冊 → 開放問題#1 應明確列出此案例作為裁決輸入,而非以
「邊緣情況」帶過。*(UI/UX 視角)*

`[P1]〔6. 開放問題#2〕`開放問題稱「`docs/ui-ux-guidelines.md` 沒有送出前
二次確認的既有模式」與事實不符——`CompleteProfile.tsx`(約 line 234-270)
同一支 `handleSubmit` 內已用 `showNotification`/`NotificationCard`
(`type:'warning'`、`details` 回顯欄位值、`confirmText`/`cancelText`)對
推薦碼做送出前二次確認,語意與規劃書舉例的「請確認姓名與身分證一致」
幾乎一致 → 開放問題#2 應更正為「是否沿用既有 `showNotification` 模式」,
而非評估發明新互動模式,決策成本大幅降低。*(UI/UX 視角)*

`[P1]〔6. 開放問題#2〕`若最終裁決要加二次確認,規劃未考慮它會與既有推薦碼
二次確認(同一 `handleSubmit` 內)疊加成連續兩個獨立跳出的確認 modal,
放大行動版註冊流程本就偏高的放棄風險 → 開放問題#2 一併討論是否合併為
單一「請確認以下資訊」對話框(姓名＋推薦碼一次列出),而非疊加兩次獨立
呼叫。*(UI/UX 視角)*

`[P1]〔6. 開放問題〕`「既有錯誤資料是否要處理」只問「截圖這一筆是否要
通知更正」,沒有涵蓋「資料庫目前還有多少筆 `profiles.name` 不含中文
字元」的規模清點——這正是這次需求的觸發情境本身(偶然看到一筆,不知道
還有幾筆)→ 開放問題應拆分:是否需要一支唯讀報表列出現有非中文姓名帳號
清單供營運評估規模,這與「要不要動手清洗」是獨立、低成本的決策。
*(需求視角)*

`[P1]〔6. 開放問題〕`規劃沒有盤點 `profiles.name` 現有自動化寫入者是否
相容新規則——`e2e/journey/run_state.py` 的 `JourneyUser.name =
f"測試{run_id}{node}"`(中文字+數字+英數代號混合)若最終裁決選擇「必須
全為中文字元」的嚴格版,會讓 journey 套件在註冊階段全滅;journey 不能在
本機跑,只在排程或晉升 PR 才會發現,屬於晚且貴的失敗點 → 開放問題#1 的
裁決應把這個相容性列為輸入之一,或在階段切分註明「若選嚴格版,需同步改
`run_state.py`」。*(需求視角)*

### P2

`[P2]〔5. 階段切分〕`前端 `validateName`(node/Vite)與後端新驗證函式
(Deno)分屬兩個隔離 runtime,規則勢必各自寫一份程式碼;規劃雖立意避免
重蹈 `validateNationalId`「前端有、後端缺席」的覆蓋率落差,但沒提出防止
兩份規則「內容本身」日後漂移的機制,而這正是同一類問題上次失效的原因
→ 階段 2 測試矩陣加入前後端共用的合法/不合法姓名範例清單(fixture),
兩側測試都跑同一份清單。*(系統、需求兩個視角皆提出)*

`[P2]〔架構影響〕`規劃未提及同 PR 更新 `docs/uknow-software-specification.md`
§4.2「真實姓名」列——同表「手機號碼」列已用「格式驗證」記錄同類規則可循;
`scripts/check-spec-drift.py` 不會機械抓到這個特定落差 → 在「階段切分」
或 PR checklist 加一句「同 PR 更新 §4.2 姓名列」。*(系統、架構兩個視角
皆提出)*

`[P2]〔2. 系統設計〕`規劃書內兩處錯誤訊息草稿彼此不一致(「請填寫身分證
上的本名」vs.「例:王小明」),也不同於 `validateNationalId`/
`validatePhone` 已建立的「規則說明＋(例:…)」同句格式 → 收斂成單一版本
並比照既有括號夾例句格式,如「姓名需包含中文字(例:王小明)」。
*(UI/UX 視角)*

`[P2]〔4. UI/UX〕`姓名欄位錯誤呈現沿用既有 `FieldError`,但全表單欄位都
未接上 `aria-invalid`/`aria-describedby`——`getInputAriaProps`
(`formHelpers.tsx:33-39`)已定義卻全專案零元件使用 → 這次修改姓名欄位
驗證邏輯時順手接上,範圍只限本次觸碰的欄位,不擴大到其他欄位。
*(UI/UX 視角)*

## 需人工裁決

`〔需人工裁決〕`驗收情境提到姓名可含「`·`」等常見姓名符號,但未指定具體
Unicode 字符——戶政系統對原住民姓名習慣使用的間隔號字符,是否與規則實作
最終採用的字符碼點一致待查證(常見有視覺相近但碼點不同的字符,誤用會
誤擋合法姓名,與上方 P1 的 `HAS_HAN` 事故屬同一類風險)。reviewer 環境
無法查證戶政實務權威字符,建議工程實作前對照既有會員姓名樣本或戶政資料
確認實際字符。*(UI/UX 視角)*

## 無缺口面向(逐視角)

- **系統視角**:金流/冪等性(不觸及 PayUni webhook,`UPDATE` 天然冪等)、
  multi-step-flow 四契約(不影響 `formDraft.ts` 草稿機制)、外部整合
  (未變動 `requireAuth`/session 邏輯)、邊界條件(不適用,單筆同步檢查)、
  現況描述準確性(規劃書對程式碼的所有行號引用逐一核對皆屬實)。
- **架構視角**:模組邊界相容性(`CompleteProfile` 非 lazy、無新路由/新
  API 呼叫點)、appShell 契約(不涉及)、multi-step-flow 四契約
  (`formDraft.ts` 只做型別/長度截斷,不受影響)、DB 層決策一致性(「應用層
  防呆、不加 CHECK」與 `phone`/`birthDate`/`nationalId` 現況處理方式一致,
  非孤例)、`name` 欄位寫入路徑完整性(逐一 grep 確認僅 `/auth/register`
  與 `PUT /auth/profile` 兩條路徑)、既有 Deno 測試套件相容性(逐一核對
  不會被新驗證打壞)。
- **UI/UX 視角**:行動版優先(沿用既有 onBlur/`FieldError` 模式)、三態
  完備(純同步驗證不涉及載入態)、資訊架構(未新增入口/畫面/路由,不觸及
  `BottomNav` 五格契約)。
- **需求視角**:需求溯源(§4.2 引用與規格書原文一致,現況斷言皆有據可查)、
  驗收可測性(大致,三個驗收情境皆可轉測試)、業務規則 §5–§10(不涉及
  金額/門檻/獎勵計算邏輯)。
