## 輸出契約(reviewer 必讀)

**審查對象**:呼叫方會指明是「規劃」還是「實作 diff」,並給檔案路徑
**或**直接把內容放在 prompt 裡(輕量改動走 Plan Mode 時不落檔,你看到的
就是全文——照樣審,不要因為沒有檔案路徑就要求對方補)。
- 審**規劃**(`/review-plan`):看設計是否正確、完整、可實作
- 審**實作 diff**(`/review-implementation`):除了你本身的視角,**必問一題
  ——實作有沒有偏離 plan?** 偏離未記錄在 PR「偏離規劃說明」的,一律至少
  P1。規劃審過、實作走偏是最常見的失敗模式,這一關專門攔它

**嚴重度定義**:
- **P0(阻擋)**:照此規劃實作會做錯功能、壞既有行為、或造成資料/資安事故
- **P1(應改)**:規劃有實質缺口,實作前應補——不補則實作期必然撞牆
- **P2(建議)**:有更好的做法,不改也能正確交付

**每項發現的格式**:`[P?]〔規劃書章節〕缺口一句話 → 建議一句話`

**逃生口(合格產出的一部分)**:
- 某面向檢視後無缺口 → 明確寫「無缺口」,**禁止為交差發明問題**
- 不確定是否為真問題 → 標「〔需人工裁決〕」,不要自行定性
- 只報缺口,不報風格偏好

**聚合規則(主 session 必讀)**:只彙整、去重、排序,**不改判**——severity
以 reviewer 原判為準;要降級或剔除任何發現,必須列入「需人工裁決」並附理由。

## v2 發現清單(依嚴重度排序)

### P0

`[P0]〔6. 開放問題#1 / 2.1 規則表〕`間隔號問題被寫成「開放問題」,但
§2.1 規則表與階段 1 驗收標準已把「不接受標點符號」當**已拍板的設計**在
執行——兩者矛盾,而後續只讀規則表的實作者會直接照拍板版落地。實質後果:
《姓名條例》賦予台灣原住民以漢字音譯登記法定姓名的權利,身分證標準格式
即含間隔號(`谷辣斯·尤達卡`),新住民歸化漢名亦同;這些人**今天可以正常
註冊**(現行 `validateName` 不檢查內容),照 v2 規則實作後中文模式判非法、
外文模式也進不去(姓名是漢字不是羅馬拼音),等於**規劃親手新增一條迴歸**,
且直接違反本功能自身目的(確保填的是身分證上的姓名)→ 此項須比照 DB GRANT
那個 P0 給予同等阻擋力(列入處置表、開工前檢查),不能停留在「建議開工前
確認」的軟性提醒;若裁決放行,需一併指定接受碼點(`·`U+00B7、`‧`U+2027、
`・`U+30FB)與是否做輸入正規化。
*(UI/UX 與需求兩個視角獨立判為 P0,理由一致:這是「壞既有行為」而非
「未支援新案例」。)*

`[P0]〔2.3 / 3. 撤銷安全性查證〕`§3 的六面向窮舉**漏掉第七條寫入路徑**:
`handle_new_user()`(`20260620000003_functions_and_views.sql:55-56` 建
`AFTER INSERT ON auth.users` trigger,`20260620000009:48-59` 定義)直接把
`coalesce(new.raw_user_meta_data ->> 'name', '')` 寫進 `profiles.name`。
`raw_user_meta_data` 是任何人呼叫公開的 Supabase Auth `/auth/v1/signup`
時可任意帶入的 `data` 參數(**只需 anon key,免登入 token、免通過 OTP**),
且該函式是 `security definer`,以擁有者權限執行 INSERT——**撤銷
authenticated 的欄位 GRANT 與兩個 Edge Function 的新驗證對它完全無效**。
本專案自己的 `test-helpers.ts:38-46` 正是用這個機制帶入 `name`,證實路徑
是活的。漏網原因:§3 第 3、4 點只掃 `index.ts` 內 `.from('profiles')` 呼叫
與 migrations 內的 **UPDATE** 陳述式,`handle_new_user` 是 **INSERT**,
兩種掃描都不覆蓋 → 開工前須處理(建議比照 `birth_date` 現行作法:不從
metadata 帶入,讓 Step 2 的 `/auth/register` 以已驗證值覆寫),或在 §3
明確記錄此殘留風險並說明為何刻意不堵;無論如何都要改掉「六面向窮舉、
無任何依賴」這個過度保證的措辭。
*(需求視角判 P0:路徑對外可達,前端不帶 metadata 不構成保護。架構視角
獨立發現同一路徑但判 P2:理由是前端目前不帶 `name`、恆寫入空字串,屬
「目前無害但需留意」,並建議在 `handle_new_user()` 定義處加註解提醒。
**依聚合規則不改判,兩個 severity 併陳供人裁決。**)*

### P1

`[P1]〔2.1〕`「切換鈕純粹是呈現層、後端靠內容自動判定」的設計讓切換鈕
**對驗證結果毫無強制力**:停在預設中文模式、從未觸碰切換鈕的使用者,輸入
`Peter`、`Admin` 這類首字母大寫的英文字串會直接通過(不含中文→自動套外文
規則),裁決 #2「預設必須全為中文字元」實際上沒有被強制。更嚴重的是
**規劃書自己列的四個不合法案例(`z1234567m`/`testuser`/`王小明123`/
`王John`)剛好都因含數字或中英混雜而被連帶擋下,沒有任何一個能暴露這個
盲點**——測試會全綠而漏洞照樣上線。連帶問題:錯誤訊息依「切換鈕狀態」
挑字,實際觸發的卻是「依內容判定」的規則,兩者會對不上(外文模式打
`王John` 觸發中文規則失敗,卻顯示「外文姓名僅限英文字母…」)→ 二擇一並
在開工前定案:(a) 讓驗證真正依切換鈕狀態把關(中文模式下含拉丁字母一律
拒絕),使「預設」有強制力;或 (b) 維持內容自動判定為單一事實來源,但
明文記錄這是刻意取捨、錯誤訊息改依「實際觸發的規則」選字,並在案例表補上
「預設模式下輸入格式工整的外文姓名」這個目前完全沒被涵蓋的案例。*(架構)*

`[P1]〔2.1〕`「前後端判定完全一致」沒有程式碼機制保證,只靠有限樣本的
共用案例表。後端沿用既有 `HAN_RANGE`(`㐀-鿿豈-﫿`),
但前端 `profileValidation.ts` 目前**完全沒有**中文判定邏輯,這次得從零新寫
一份,兩個 runtime 無法共用常數;若前端用了更常見但範圍較窄的
`一-龥`,對 CJK 擴充 A 區(`㐀-䶿`)與相容表意文字
(`豈-﫿`)邊界字元會前端拒絕、後端放行 → 要求前端正則逐字複製
並註解對照 `index.ts` 出處,案例表加入這幾個 range 邊界字元當機械探針。
*(系統)*

`[P1]〔2.2〕``formDraft.ts` 的 `MAX_LEN.name` 若照字面「同步」留在 10,
外文使用者填 `Christopher Nolan` 後遇頁面卸載重整,草稿還原會靜默截斷成
`Christophe`——**而截斷後的字串仍會通過格式驗證**,等於把一個格式合法但
錯誤的姓名寫進這個要用來比對提領身分的欄位,使用者未必察覺。這正是本功能
想避免的「等到提領才發現」情境,由規劃自己製造 → 明確寫出 `MAX_LEN.name`
須取**兩模式上限中較寬鬆者**(草稿層只是防炸儲存體的粗篩,不需也無法做
模式相依的精準把關),並在階段 4 加「外文長姓名存草稿、重整後不被截斷」
的回歸測試。*(系統、架構兩視角獨立提出)*

`[P1]〔3 / 5 階段4〕`模式狀態納入草稿白名單的方式未定義,有型別落差:
`sanitizeDraft` 現有兩條消毒路徑是「`MAX_LEN` 驅動的字串截斷」與
「`agreedToTerms` 的 boolean 嚴格檢查」,而模式狀態本質是只有 2 個合法值
的 enum;若直接掛進 `MAX_LEN` 沿用字串截斷,被竄改的 sessionStorage 值
(如 `"xyz"`)會被當成合法草稿原樣寫回 UI state,打破該模組檔頭註解揭示的
「型別不符即丟棄」設計原則 → 仿 `agreedToTerms` 的 allow-list 檢查,並把
`ProfileDraft` interface 與 `CompleteProfile.tsx` 的 `EMPTY_FORM` 一併列入
階段 4 異動清單(規劃目前兩者都沒列)。*(架構)*

`[P1]〔2.4〕`新驗證函式對非字串 `name` 的防禦未寫明。`PUT /auth/profile`
的觸發條件 `'name' in body` 只檢查鍵存在、不檢查型別,`body.name` 可以是
`null`/數字/物件;而 `HAN_RANGE` 那段註解記載的正是「未防禦邊界輸入導致
500」的事故,同檔 `verifyNationalId` 的 `(idNumber ?? '').trim()` 對數字
一樣會拋未捕捉例外——同類疏漏在此 codebase 不是第一次 → 要求新函式先做
`typeof name === 'string'` 防禦、回傳「格式不符」而非拋錯,並把
`{name:null}`/`{name:123}` 加入階段 2 案例表。*(系統)*

`[P1]〔5 階段3〕`階段 3「以使用者 token 建 client 直寫應失敗」**現有測試
基礎設施完全不支援,規劃未提及需要新 helper**。`test-helpers.ts` 只有
`adminClient()`(service_role)與 `getUserAccessToken()`,後者回傳的 token
在既有測試中一律只餵給 `app.request()`(Hono in-process),不經過
PostgREST 閘道。要真測「使用者 token 直寫 `/rest/v1/profiles` 被拒」需對外
發真 HTTP 請求且同時帶 `apikey`(anon key)+ `Authorization`,而整個
`supabase/functions/**` 沒有任何 `SUPABASE_ANON_KEY` 的讀取或本地 fallback
(對照 `SERVICE_ROLE_KEY` 在 `test-helpers.ts:12-13` 有本地 demo fallback)
→ 規劃應明列「新增 anon key 常數 + PostgREST 直連 helper」為階段 3 的前置
工作,而非隱含在一句話裡。*(系統)*

`[P1]〔5 階段2〕`階段 2 的驗收標準「通過驗證的姓名經 `maskNameByGen(gen=2)`
必為中文遮罩樣式」需直接呼叫該函式,但 `maskNameByGen`(`index.ts:2386`)
**未 `export`**,目前也無任何測試引用。規劃 §2.4 只要求新驗證函式 export

可安全匯出),否則這條驗收標準寫不成 `.unit.test.ts` 的直接斷言。*(系統)*

`[P1]〔2.2 / 4〕``CompleteProfile.tsx` 現有 onChange 長度守衛是**靜默丟棄
超限按鍵、不顯示任何錯誤**;若該守衛綁「切換鈕模式」,外文使用者在預設
中文模式(上限 10)下沒注意到切換鈕,打到第 10 字元後按鍵直接被吞,連一句
可查找的錯誤訊息都沒有——比驗證錯誤更難察覺的死巷 → 明訂「打字階段一律
放寬到兩模式上限中較大值,超限與否留給 blur 驗證訊息處理」,不要靜默吞鍵。
*(UI/UX)*

`[P1]〔2.2 / 4〕`「切換模式時已輸入內容如何處理」未定義:純中文內容切到

`[P1]〔4〕`切換鈕的視覺形式與位置未定案(「上方或右側」二選一未決),

`[P1]〔4〕`確認框合併只寫「把姓名加進 `details` 陣列即可,標題與訊息改為

`[P1]〔4〕`合併後 `hasConfirmedReferralCode` 旗標**只在推薦碼變更時重置**

`profiles.name` 唯一被看到的地方是 `WithdrawalManagement.tsx:62` 這類

## v1 發現清單(依嚴重度排序)

### P0

`[P0]〔2. 系統設計〕`「不加 DB constraint」的決定未查證 `profiles` 表既有
寫入路徑——`20260620000009_auth_profile_hardening.sql` 已對 `authenticated`
角色開放 `name`/`phone`/`birth_date`/`national_id`/`bank_code`/`bank_account`
的直接 UPDATE GRANT,搭配 RLS `profiles_update_own`(`id = auth.uid()`,
`20260620000002_rls_policies.sql`),任何登入用戶可直接打
`PATCH /rest/v1/profiles` 寫入任意姓名,完全繞過規劃唯一的防線
(`POST /auth/register`、`PUT /auth/profile` 兩個 Edge Function 端點)。
`profiles` 表上僅有的 BEFORE UPDATE trigger(`trg_profiles_updated`、
`trg_profiles_no_escalation`)都不管姓名格式。規劃自陳的核心動機之一
(擋掉「任何持有效 token 的使用者直接打 API 把姓名改成任意字串」)照此規劃
實作後依然成立,只是換一個不需要理解 Edge Function 契約、更直接的路徑
→ 三選一裁決:①撤銷 `name` 欄位的直寫 GRANT,逼所有寫入走
service_role(Edge Function);②比照既有 `trg_profiles_no_escalation`
(`20260620000003_functions_and_views.sql:75-77`)前例,加 BEFORE UPDATE
trigger 或 CHECK constraint 做最後防線;③在規劃風險章節明文接受此殘留
繞過面並寫明理由。不要用「決定不加」的篤定語氣掩蓋一個其實查得到答案的
技術事實。
*(系統視角原判 P1、建議同樣的三選一;需求視角原判 P0,認為規劃如實作
將無法達成自陳的核心防線目的。兩者是同一缺口的獨立發現,severity 判斷
不同,予以如實保留,兩份原始論證都成立,如何裁決留給人工。)*

### P1

`[P1]〔3. 架構影響〕`規劃新增的姓名格式驗證函式未提及重用
`maskNameByGen` 正上方既有的 `HAS_HAN`/`HAN_RANGE` 正則
(`supabase/functions/api/index.ts:2380-2382`,範圍
`㐀-鿿`+`豈-﫿`)——該正則的註解記載過一次真實事故
(NFC 正規化誤判導致 emoji 姓名觸發 500)。若新函式獨立重寫判斷邏輯:
一是可能重蹈同一 Unicode 邊界陷阱;二是可能與 `maskNameByGen` 對「什麼算
中文姓名」的認定不一致,導致「通過驗證的姓名,遮罩卻仍顯示英數樣式」,
原地重現這次問題的觸發症狀本身(推薦網絡頁看到英數風格遮罩名)→ 新函式
明確重用或至少匯出/對齊 `HAS_HAN`/`HAN_RANGE`,並加測試釘住「通過
`validateName` 的姓名,`maskNameByGen(gen=2)` 必為中文遮罩樣式」。
