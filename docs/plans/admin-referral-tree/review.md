## 發現清單（依嚴重度排序）

### P1

- **[P1]〔§6 Q3、§2.2、§4、§5 階段 4〕異常清單入口違反 W6-7 的預設**（需求）。W6-7 明確推翻「異常清單」，但 §2.2、草圖與階段 4 已把 `/anomalies` 和「⚠ 異常 N」當成既定設計。
  - 建議：預設不做，從本文移除；只有業主在 Q3 裁決要做，才放回來。
- **[P1]〔§1 情境 4、§6 Q1〕「停權／到期不影響入帳」已寫進驗收**（需求）。Q1 還沒裁決，驗收卻已經寫定。另外，「自領停發」等於成環停發（`referral_cycle_detected`），規劃沒有明寫這個對應。
  - 建議：驗收情境 4 加註「待 Q1」，並明寫對應關係。
- **[P1]〔§5 階段 10～11、Q8〕S3b 對帳口徑改寫了業主的字面定義**（需求）。業主寫的是「餘額 ≠ 獲得 − 提領」，規劃改成四條跨表不變式。這題由主 session 決定不夠，「點數來源明細」的內容也還沒定義。
  - 建議：Q8 改成需要業主確認。
- **[P1]〔§2.2 換線紀錄、Q2(a)〕`referral_pair_history` 不是換線紀錄**（系統）。它在任務 +1 時才寫入，`created_at` 不是接線時點，回填列的 `created_at` 全部相同，有些推薦關係根本沒有列。「A→B→A 得到正確序列」這點沒有驗證過。
  - 建議：(a) 只承諾「曾出現過的推薦人集合（無序）＋新約付款單事件（有序）」；要完整、有序的紀錄就走 (b)。階段 3 的驗收要依照真實資料形態重寫。
- **[P1]〔§2.2 換線失敗判定〕「比對付款後的推薦人，或查告警」兩種判法都不穩**（系統）。A→B→A 時比對現況會誤判；告警的種類會因 S6 而漂移；`fresh_referrer_source='keep'`、新舊推薦人相同的單也不是換線。
  - 建議：明定判定式。換線成功時 `referred_by_changed_at` 會等於 `completed_at`，可以用來判定，但只對最近一次變動成立。判不出來時顯示「未能確認」。
- **[P1]〔§2.1 可判定閘門〕「推廣到鏈上每一位」是新口徑，不是「與自癒一致」**（系統）。`repair_orphaned_payments` 只檢查付款人本人，補發時讀的是現在的鏈，所以「自癒補得到的才叫缺漏」這句不成立。
  - 建議：明寫「比自癒更保守」。祖先換過線的情況不要顯示「自癒會補發」的提示。任務續約的時點改用 `claimed_at`；付款單要經 `subscriptions.source_payment_order_id` 取得 `subscription_id`。
- **[P1]〔§2.2 節點、搜尋、頂層〕樹的父子關係沒有指定單一來源**（系統）。第 1 代讀 profiles，第 2、3 代讀 edges，兩者可能不一致，同一個人會出現兩次或消失。Q5 的過濾如果也套在子層，`directCount` 就對不上。
  - 建議：
    - 樹一律以 edges 為來源，profiles 與 edges 不一致的另標異常。
    - Q5 只套頂層。
    - 分頁用穩定排序（`created_at, id`）。
- **[P1]〔§3 後端〕`deriveNodeStatus`「改成 export」會造成循環匯入**（架構）。`referral-invite.ts` 有「不得 import ./index.ts」的守衛。
  - 建議：抽成獨立模組（例如 `api/node-status.ts`），index.ts 與新 handler 都 import 它，並守住既有呼叫點的行為。或者改走 deps 注入，加上反向匯入守衛測試。
- **[P1]〔§3 前端、階段 7～8〕前端資料注入鏈漏寫**（架構）。現況是 `AdminDashboard` 定義 loader，經 `AdminConsole` 傳到 `MemberManagement`。
  - 建議：
    - 用單一 `referralTree: ReferralTreeLoaders` 物件整包傳下去。
    - 寫明新次分頁怎麼參與 `tabLocked`／`lockedTabProps`。
    - 寫明「在推薦樹中查看」的目標 id 由誰持有。
    - `MemberManagement` 已經超過 900 行，避免再加欄位。
- **[P1]〔§5 階段 5〕「500 不回空清單」在 DB 測試裡紅不了**（架構）。
  - 建議：拆出 `admin-referral-tree.unit.test.ts`，用假 deps 測 400、404、500 與 rpc 錯誤。DB 測試只留守門與契約。另補一條反向匯入守衛。
- **[P1]〔§4 詳情 Sheet〕「異常」排在最後一區**（UI/UX）。375px 要捲到底才看得到，八區平鋪、沒有主狀態。
  - 建議：依 §13 第 3 條，把異常用 `StatusCallout warning` 放在最上方，沒有異常就不渲染；首屏要直接回答「有沒有發錯」。
- **[P1]〔§4 付款與三代獎金〕手機版面沒有設計**（UI/UX）。
  - 建議：
    - 手機一筆付款一張卡，卡內三行，每行「誰 · 金額 · 結果徽章」。
    - 用 `useMediaQuery` 擇一渲染手機或桌面版。
    - 文字用 `min-w-0 wrap-anywhere`。
    - e2e 把新路由加進 `test_overflow_sweep.py` 的 `ROUTES`（要切到子分頁才量得到）。
- **[P1]〔§4 推薦人鏈「可點跳去該人」〕Sheet 內跳到另一人的導覽模型沒有定義**（UI/UX）。要決定的有：替換內容還是疊一層、返回、Android 返回鍵、焦點與捲動、樹上選取是否同步。
  - 建議：替換內容，頂部放「返回〇〇」，並記錄跳轉堆疊（〔需人工裁決〕兩案取捨）。
- **[P1]〔§3「在推薦樹中查看」〕跨次分頁的導覽沒有規劃**（UI/UX）。要依序處理：關閉 Sheet 並歸還焦點、切換 `memberTab`、處理 `lockedTabProps`、依 id 載入並自動展開。
  - 建議：寫進階段 8 並補測試。
- **[P1]〔§4 三態〕缺四塊的三態**（UI/UX）：
  - 詳情 Sheet 本身的骨架、失敗、404 三態。
  - Sheet 內兩支請求的失敗不連坐。

  - 搜尋的失敗態（要和「找不到」分開）、`useRetryFocus` 的焦點落點、頂層的空態。
- **[P1]〔§4 自動展開、`p_ensure_id`〕失敗與一致性的路徑沒有定義**（UI/UX）。中途某層失敗時停在哪、怎麼重試；`pinned` 併入後 X / Y 與 offset 怎麼算（重複或跳號就是靜默截斷）；展開中的狀態提示；`scroll-mt-20` 與 `tabIndex=-1`；播報用常駐的 live region。
