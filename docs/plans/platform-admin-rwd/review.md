## 發現清單（依嚴重度排序）

### P1

**F1 [P1]〔§2 系統設計 / §4.1 匯款作業面板〕（系統）**
匯款作業面板顯示哪一筆，完全由 `activeId` 決定，而它**唯一的寫入點**是
`TableRow onClick={() => setActiveId(w.id)}`（`WithdrawalManagement.tsx:768`）。
§4.1 只描述手機卡片要顯示哪些*欄位*，沒說卡片是否接手這個職責——桌面表格
在手機被拿掉後，`activeId` 沒有任何寫入路徑，作業面板會永遠釘死
`withdrawals[0]`，展開也切不動。這正是「本次只改同一份資料怎麼排版」不成立
之處：排版變更悄悄拿掉了一個互動。
對照組：`MemberManagement` 的「查看」是顯式按鈕（`:111`），不依賴 row 結構，
轉卡片沒有這個問題——所以這不是表格轉卡片的通例陷阱，是本元件特有的隱性耦合。
→ 建議：在 §4.1 明確定義手機卡片是否要有等同的「設為目前作業對象」互動
（卡片本身或卡片內一顆按鈕觸發 `setActiveId`），或明確裁決「手機版作業面板
固定顯示第一筆、不提供切換」並寫進 §4.1。兩者皆可，但不能沒答案。

**F2 [P1]〔§4.1 頂層 Tabs / §4.0 P1〕（UI/UX）**
`grid-cols-3 md:grid-cols-5 + h-auto` 這組 class 清單**漏了無前綴的 `grid`**，
依字面實作很可能是 no-op。`TabsList` 原語預設 `inline-flex ... flex`
（`ui/tabs.tsx:32`），`grid-cols-*` 只是 `grid-template-columns`，對
`display:flex` 容器毫無作用。現況碼 `AdminDashboard.tsx:122` 的
`w-full md:grid md:grid-cols-5` 已自證這點——作者刻意在 `md:` 明寫 `grid`
才能覆寫 base 的 `flex`。若照字面做，手機容器仍是 flex（無 `flex-wrap`），
標籤維持單行 + `overflow-x-auto` 接手捲動，**P1 完全沒被修好、U2 驗收落空**。
→ 建議：§4.1 寫出完整 class（至少含無前綴 `grid`），階段 1 的驗證標準也要
能量出「兩列排列」而不只是「TabsTrigger 存在」。

**F3 [P1]〔§5 階段切分 / §7 風險表 / §8 可測試性〕（架構 + UI/UX，同一缺口）**
五個階段裡**沒有任何一項對純 CSS 版面修改做「真瀏覽器渲染且會擋 CI」的驗證**。
jsdom 不跑版面引擎，只能斷言 class 字串或 DOM 結構存在，量不出 P1（TabsList
兩列）、P5（Dialog 寬度）、P6（雙圖）、P9（Sheet 的 `dl`）是否真的照預期渲染。
唯一碰真瀏覽器的階段 5 是 report-only（`STRICT` 是套用到全部 `ROUTES` 的
單一全域開關，`SweepRoute` 無逐路由 override），而且該檔自己文件化
「對話框／下拉／Sheet 需要點擊才開啟」是已知盲區（`test_overflow_sweep.py:352`）
——P5/P6/P9 剛好全在 Dialog/Sheet 裡，階段 5 擴充後仍掃不到。
**上面的 F2 就是這個驗證缺口會放過的典型案例**：規劃內所有測試都會綠燈，
使用者看到的仍是壞的。
（同一缺口再一例：`TabsList` 若把 `h-9` 換成 `h-auto`，`TabsTrigger` 未同步
調整的 `h-[calc(100%-1px)]`（`tabs.tsx:53`）在 auto-height 容器下的百分比
高度解析，也只有真瀏覽器才確認得了。）
→ 建議：為涉及實際版面呈現的驗收標準（尤其 U2「五個分頁標籤同時可見」、
U3「照片寬度貼齊螢幕」）補一項會擋 CI 的量測（Playwright `getBoundingClientRect`
量 TabsList 是否分兩列、Dialog 寬度與視窗邊界的間距）；並評估讓 `SweepRoute`
支援逐路由 `STRICT` override，不必動全域開關。§7 該列風險的「緩解」文字也要
誠實反映現況。
**（已全數處置。** 能力面見下方「M1 已處置」；文字面已回填 `plan.md`：
§4.3 寫明 jsdom 量不出版面與兩支探針的分工、§5 的每個階段驗證標準改成真實
幾何量測並明列要刪掉哪幾條 `known_overflow` 與 xfail marker、§7 該列風險改為
誠實陳述「jsdom 不再是唯一防線」。CI 證據：PR #242 的 `e2e-tests` 軌綠。**）**

**F4 [P1]〔§3 動到的模組 / §4.1 觸控〕（需求判 P1；UI/UX 判 P2）**
`ui/checkbox.tsx` 的 `pointer-coarse` 改動 blast radius 超出 §3 清單：該元件
還被 `WithdrawalProcess.tsx`、`JoinReferralProgramDialog.tsx`、`CompleteProfile.tsx`、

**F5 [P1]〔§3 動到的模組 / §5 階段切分〕（需求）**

### P2

**F7 [P2]〔§4.0 P5〕（UI/UX）** — P5 的**診斷結論與修法方向正確**，但量化的
症狀描述站不住腳。`DialogContent` 同時帶 `w-full`（`dialog.tsx:41`）；對
`position:fixed` 元素，`width:100%` 已依視窗寬度定值（祖先鏈 `globals.css`、
`App.tsx` 的 `<main>` 均無 `transform`/`filter`/`will-change` 建立新包含區塊），
`max-width` 比目前寬度大時不生效。真正的後果是**失去 `calc(100%-2rem)` 的
左右 1rem 安全邊界、對話框貼齊螢幕邊緣**，不是產生 768px 寬度與水平捲動。
→ 若日後拿「是否出現水平捲軸」（`scrollWidth > innerWidth`）當驗證依據，
永遠測不出這個真正的退化。改量 dialog `getBoundingClientRect` 相對視窗邊界
的間距。

**F8 [P2]〔§3 偏離理由 1〕（架構）** — 「同一檔案裡一半靠 CSS 一半靠 JS 是
兩套真相」這條理由**只在 `WithdrawalManagement` 成立**（它已有 W8 的
`isDesktop`）；`MemberManagement` / `SystemAlerts` 目前完全沒有既有 JS media
邏輯，對這兩檔套用同一條理由，等於用另一個檔案的既存包袱正當化「無中生有」
引入 `useMediaQuery`。真正對三檔都站得住的是理由 2（DOM 成本）與理由 3
（可測試性）。→ 若 Q3 通過、§7 要補判準文字，判準不該照抄理由 1 的措辭，
只用理由 2/3 立論，避免未來規劃拿一個對其他元件不成立的先例套用到別處。

**F9 [P2]〔§3 / 共用原語〕（架構）** — 三個元件會各自呼叫
`useMediaQuery('(min-width: 768px)')`，測試側的 `stubMediaQuery`（~12 行，
`WithdrawalManagement.test.tsx:25`）也會在階段 2–4 的測試檔各自重貼一份——
這正是 `useMediaQuery.ts` 檔頭註解點名要避免的模式。→ 建議階段 1 順手抽出
共用的 `stubMediaQuery` test util（比照 `StatCardGrid` 的抽取先例）。
卡片 markup 本身**不建議**強行抽共用元件——三張卡的欄位/操作鍵差異夠大
（11 欄+5 Dialog vs 8 欄+3 鍵 vs 6 欄+JSON 收合），抽象成本可能高於重複成本。

**F10 [P2]〔§3 / 長期成本〕（架構）** — `WithdrawalManagement.tsx` 已是全 admin
最重的容器（849 行，狀態管理 + 5 個 Dialog + CSV 匯出全在一檔），階段 2 要再
疊一整套卡片渲染，半年後會逼近甚至超過 1000 行、身兼「業務邏輯 + 兩套完整 UI」。
規劃完全沒提是否拆分。→ 建議把手機卡片列表抽成同資料夾子元件
（如 `WithdrawalCardList.tsx`），用 props 接住 record 與既有 handler——與 §7
風險表「共用同一組 handler 與同一個 record 物件」方向一致，甚至更容易靠型別強制。
`MemberManagement`（474 行）風險較低但精神相同；`SystemAlerts`（147 行）可不拆。

**F11 [P2]〔§1「不做什麼」〕（需求）** — 第 3 項「不改 W8 的行動端權限邊界」被
放進**明確排除**清單本體，但同一句話又引用 Q1（未裁決的開放問題），與清單其他
三項（已定案的排除）性質不同，構成清單內部語意不一致——讀者可能誤把它當定案。
→ 改標注為「預設維持（見 Q1），非最終定案」，或只留在 §6。

**F12 [P2]〔§1 U4 / §5 階段 3〕（需求）** — U4 的「三顆操作鍵都在拇指可及處
**且 ≥44px**」是複合驗收標準，但階段 3 的驗證標準弱化成「三顆操作鍵可達」。
「拇指可及處」是版面位置的人因判準，jsdom 量不出 viewport 幾何。這是 jsdom 的
固有限制、不是規劃的錯，但規劃沒有承認這個落差，讓驗收標準看起來全部可自動驗證。
→ 階段 3 驗證標準明確切分「≥44px 與存在性由測試釘住；拇指熱區位置由人工目視驗收」。

**F13 [P2]〔§5 階段 2 驗證標準〕（架構）** — 「桌面：既有 40 條測試全綠不改」
數字有誤，`WithdrawalManagement.test.tsx` 實際是 **26 個** `it(...)`。
（三檔加總 477+332+166=975 行與規劃書宣稱的「975 行」完全吻合，顯示規劃確實
查過 codebase，只是這處條數寫錯。）不影響「全綠不改」這道真正的閘門。
→ 訂正數字，避免實作者對照時去找不存在的 14 條測試。
**（已於本次修訂處置，見下方「處置」節。）**

### N0 —— 查證後**不成立**，記錄以免日後重複懷疑

主 session 原本懷疑階段 5 讓 `/admin` 用同一個 `path` 掃五次，會在報告裡
互相覆蓋。查 `e2e/test_overflow_sweep.py` 的 `_write_report`：`results` 是
**list**、以 `label` + `path` 一起呈現、按發現數排序，重複 path 不會撞 key。
**這不是問題**，不列為發現。

### N1 [P1]〔§5 驗證標準〕覆蓋率棘輪會擋 CI，而規劃從頭到尾沒提

`npm run check`（＝ pre-commit 跑的那個）**不含覆蓋率**：
`biome check && tsc --noEmit && vitest run && knip`。覆蓋率門檻是 CI 另外跑
`npm run test:coverage` 把關（`.github/workflows/ci.yml:243`）。

門檻 `functions: 54`，而 2026-07-26 的實測值是 **55.21——只有 1.2 點餘裕**
（`vitest.config` 的棘輪註解自己寫了這個數字）。規劃要在 `AdminSetup.tsx`
與 `SystemNotifications.tsx` 這兩個**目前零測試檔**的元件上加新 JSX，而 §5
的驗證標準只寫「vitest 綠」。

**後果：本機 `npm run check` 全綠不等於 CI 綠。** 這條會在階段 4（或更早，
若 F5 的 `AdminSetup` 改動照現況無測試落點地做掉）撞牆。
→ 建議：§5 每個階段的驗證標準加上「`npm run test:coverage` 四項門檻不降」，
並把 `AdminSetup.tsx` / `SystemNotifications.tsx` 的測試檔視為**前置條件**
而非可選項。

### N2 [P1]〔§4.1〕規劃指定用裸 `<details>`，但 repo 已有對應原語

`src/components/ui/collapsible.tsx`（Radix Collapsible）**已存在**，且
`CreateServiceProvider.tsx` 與 `EditServiceProvider.tsx` 都在用；
全站 `<details>` 用量是 **0**。

規劃在兩處指定 `<details>`——匯款作業面板摺疊（§4.1）與告警 `context` JSON
收合（§4.1）——等於在既有原語可用的情況下另起爐灶。這正是
`ui-ux-guidelines.md` 前言「規劃要發明新模式，得先說明為什麼既有模式不適用」
要擋的事，而 §4.1 沒有說明。

附帶代價：`<details>` 的開合狀態**不受 React 控制**，測試斷言方式與 Radix
那套不同，會在 admin 底下長出第二種摺疊慣例。
→ 建議：改用 `Collapsible`，或在 §4.1 寫明為什麼 `Collapsible` 不適用。

### N3 [P2]〔§3 / §5 階段 1〕「標題區字級」是一個無證據的承諾

§3 的模組表與 §5 階段 1 都列了「標題區字級」，但 **§4.0 的 P1–P14 沒有對應
證據項、§4.1 也沒說要改成什麼**。而且「平台管理」四個字在 `text-3xl`（30px）
下約 120px，375px 下不會破版。

這與需求視角抓到的 **F5（`AdminSetup` 有承諾、無測試落點）是同型缺陷**，
需求視角只抓到一個。差別在於 F5 至少對應一個真問題，這條**可能連問題都
不存在**——是比漏做更糟的「承諾修一個沒壞的東西」。

## P1

**R1 [P1]〔§4.1 觸控 / §5 階段 1〕（架構 ＋ 需求，兩個視角獨立收斂）**
F4(c) 的熱區方案照字面實作是 **no-op**，而且宣稱的驗收工具量不到它。

1. class 清單漏了 `content-['']`。CSS 規範下 `::before` 的 `content` 初始值是
   `normal`（計算值等同 `none`），不生成渲染盒，`absolute` 與 `inset` 全部無效。
   主 session 覆核：本專案 Tailwind **v4.1.3**，`node_modules/tailwindcss/preflight.css:7-16`
   對 `*, ::after, ::before` 只重置 `box-sizing/margin/padding/border`，**沒有設
   `content`**（v3 的 preflight 有 `--tw-content: ''`，v4 拿掉了）；全站
   `before:` / `content-[` 用量 **0**，沒有樣板可抄。
2. `e2e/layout_probe.py:53-61` 的 `viewport_fit` 是
   `document.querySelector(sel).getBoundingClientRect()`——偽元素不在 DOM 裡選不到，
   且 `position:absolute` 的偽元素不會撐大宿主的 border box。所以即使補了
   `content`，它量到的仍是 16px 的可見方框。**驗收標準宣稱在量熱區，實際在量別的東西。**

**這是 M1 整套能力要擋的失敗模式本身**：上一次是 F2 漏了 `grid`，這次是熱區方案
漏了 `content`——而寫下這個方案的正是主 session。
→ 建議：class 補 `pointer-coarse:before:content-['']`；驗收改用**點擊命中測試**
（在 -14px 偏移的四角 `elementFromPoint`，確認仍命中 checkbox），`layout_probe.py`
加一個函式。命中測試優於讀 `getComputedStyle(el, '::before')`——後者仍是在檢查
「有沒有寫對」，前者檢查「按得到嗎」，對這類錯誤免疫。

**R2 [P1]〔§4.1 觸控 / §7 風險表〕（系統）**
熱區擴張在**密集勾選格**裡會互相重疊，F4(c) 免除回歸驗證的理由不成立。

`CreateServiceProvider.tsx:413` 與 `EditServiceProvider.tsx` 的服務區域選擇器是
`grid grid-cols-2 gap-2` 逐一渲染的 `<Checkbox>`（資料來自 `TAIWAN_REGIONS`，
台北市 12 區、新北市更多，常態 6–15 列）。每列高度由 `text-sm` 的 line-height
決定 ≈ 20px、`gap-2` = 8px，**相鄰列中心距約 28px**；`-inset-[14px]` 讓熱區上下
各延伸 22px，**重疊 16px**。使用者想勾第 5 區、手指落在交界帶會勾到第 4 或第 6 區，

降低 inset 也救不了：28px 列距下不重疊的上限是每邊 6px，熱區只有 28px，**達不到 44px**。
→ 建議（reviewer 給兩案，主 session 另提第三案，一併留給人審）：
(a) 熱區擴張改成 opt-in，只套安全的使用點；(b) 收斂幅度並重新評估 blast radius；

**R4 [P1]〔§4.1 頂層 Tabs〕（UI/UX）——結論經主 session 實測後不成立，方法論成立**
reviewer 指出「375px ÷ 3 ≈ 119px」漏扣兩層 padding（`App.tsx:294` `<main>` 的

**主 session 實測（375px、真瀏覽器、與 app 同一份字型堆疊）**：

| 量的東西 | 值 |
|---|---|
| `main` 內容寬 | **343px**（padding-x 32px） |
| 三欄 track（扣 `p-[3px]` 6px） | **112.3px** |

| 「獎金提領管理」`text-sm`/`font-medium` | **84px** |

`84 < 94.3` → **塞得下，餘裕 10.3px（12%）**。

- **reviewer 的方法論是對的**：規劃書確實漏扣 padding，而且既有註解的「約 69px」
  正是 `337 ÷ 5 = 67.4` 算出來的，證明該扣。規劃書的 119px **要訂正成 112.3px**。
- **reviewer 的結論不成立**：他沿用了規劃書那個沒有實測的「約 100px」。真值 84px。
  （順帶：既有註解說「最長標籤需要約 100px」也是高估，但它的結論仍成立——
  84px > 五欄的 49.4px 文字空間。）
- **reviewer 提的量測缺口成立且獨立於上面**：`count_rows`（`layout_probe.py:25-50`）
  只按 `top` 座標分群數列數，**不比對寬度**；`grid-cols-3` 底層是
  `repeat(3, minmax(0, 1fr))`，文字溢出格子時是 **ink overflow**（疊到隔壁分頁），
  不改變元素自己的 `getBoundingClientRect()`，兩支探針都抓不到。§7 寫的備案
  「擠不下就退回 2 欄三列」**沒有任何機制去偵測什麼時候該退**。
→ 建議：訂正數字為實測值；仍補一支「逐 `TabsTrigger` 的 `scrollWidth` 是否超出
`clientWidth`」的量測——10.3px 的餘裕不厚，而字型在不同環境會變。

**R5 [P1]〔§4.1 匯款作業面板 / §4.3〕（UI/UX）**
「點卡片就地展開」是**全新要寫的互動元件**，規劃完全沒交代鍵盤可達性與語意。
§4.3 只提卡片沿用既有 `aria-label`（那是給 checkbox 與「查看」按鈕的），沒提
**卡片本身**作為觸發器要有 `role="button"` / `tabIndex=0` / Enter・Space 處理，

與鍵盤可達性要一起想，不要再添新債」——既有債務不是複製它的理由。
