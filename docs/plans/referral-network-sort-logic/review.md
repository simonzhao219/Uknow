## 發現清單(依嚴重度排序)

### P0(阻擋——不處置不得開工)

**[P0-1]〔§1 需求 B / §2.1 Review 發現 1〕(需求)** 使用者原話「第一代先自己排好、
其第二代自己排自己的、其第三代自己排自己的」被逕自結案為「結構上已成立、只有排序鍵要改」,
這是整個 feature 的地基、規格書零依據,卻沒有任何一題進 §6 開放問題;至少有一個未被排除的
替代解讀:目前是懶載入巢狀樹,展開王大明後陳小華會插在王大明與 Alice 之間,**一代節點不再
連續**——使用者說的「第一代先自己排好」可能正是指這個呈現,而非排序鍵
→ 在 §6 增一題把兩種解讀並陳(僅換鍵 vs. 世代分組呈現),請需求方看「王大明/Alice/Zoe
展開後的實際畫面順序」確認後再開工。

### P1(應改——不補則實作期必然撞牆)

**[P1-1]〔§2.2 變更 / §6 開放問題 #2〕(系統)** search 端點在排序後才
`slice(0, SEARCH_LIMIT=50)`(`index.ts` L2529–2531),排序鍵與預設方向一改,「哪 50 個人
搜得到」就跟著換——預設由 desc 轉 asc 後回傳的是最舊的 50 位,最新加入的下線在大網絡中會
直接搜不到,而 UI 只 render `matches`、完全不顯示 `total`(`ReferralTreeView.tsx` L569–571),
截斷是靜默的 → 開放問題 #2 必須把「命中 >50 時要保留哪一批」一起裁決(建議 search 固定用
「最新在前」或改為先取前 50 再排序),並在 `network-endpoints.test.ts` 補一個 >SEARCH_LIMIT
的命中集測試把決定釘死。

**[P1-2]〔§5 階段切分 / §2.2 回應形狀變更〕(架構)** Phase 5 拿不出「斷言紅」,且規劃書
據以推理的「後端 schema 是 exact」與現況不符——`api-contract.ts` L84–92 的 `obj()` 只走
`Object.entries(shape)`,未宣告的多餘欄位一律放行,`assertShape` **抓不到**「schema 刪了、
後端還在吐」;真正逼同一 commit 的是 `buildFlatNode`(`index.ts` L2367)的 TS
excess-property check(結論仍安全,但依據是錯的,而錯的依據正好掩蓋了「payload 多餘欄位
無任何 runtime 防線」)→ 把 Phase 5 的紅燈定成「回應不得再含該 key」的執行期斷言
(`assert(!('subtreeLatestJoinedAt' in node))`,加在既有 overview 測試內),它同時解掉
紅燈與防線兩件事。

**[P1-3]〔§1 驗收情境 B4 / §5 階段切分〕(需求判 P1;系統判 P2,取高者)** 驗收情境 B4
用規劃書指定的既有種子**不可驗證**:王大明只有 1 個二代(陳小華)、陳小華只有 1 個三代(𠮷),
單子節點分支無法證偽任何層內排序——需求 B 只在一代被驗到,二/三代「自己排自己的」全靠推論
→ 種子加開(王大明下再加一個加入時間早於陳小華的二代、陳小華下再加一個三代),讓 children
端點在升冪與降冪兩方向都有可證偽的期望值。

**[P1-4]〔§3 架構影響 · localStorage〕(需求)** 「曾主動選過排序的使用者維持其選擇——
明示選擇優先,正確」是規劃者自行做的**產品裁決**,被寫成既定結論而未列入 §6:現行預設就是
`updated_desc`,凡點過排序器並停在「最新加入」的既有使用者,改版後仍是新到舊,與使用者要的
「預設舊到新」在觀感上完全相反 → 列為開放問題(是否一次性清除/遷移 `referralSortMode`),
並在 §1 驗收表補一列「回訪使用者(localStorage 已存 `updated_desc`)」的期望值。

**[P1-5]〔§4 UI/UX〕(UI/UX)** 排序鍵在列上完全不可見——需求動機是「使用者看不懂順序是
怎麼來的」,但 `NodeRow`(L175–225)只渲染 chevron/頭像/姓名/`RowAside`(剩 N 天到期 或 N 位),
加入日期只存在於點開後的詳情(L336–353);把排序鍵改對之後,使用者依然看不到任何可佐證順序
的資訊 → 排序為 `updated_*` 時在列上露出加入日期(`formatTwDate` 已有),並明確定義它與
`RowAside` 既有優先序(到期倒數 > 分支數)的關係;若需求方只要改鍵,請在 §1「不做」清單
明文寫入這一條,別讓它靜默落空。

**[P1-6]〔§1 驗收情境 A1 / §4〕(UI/UX)** 驗收條件「首次進頁面排序器顯示『最舊加入』」
在手機上不成立——排序晶片的文字層是 `hidden sm:grid`(L520),手機是純 icon,狀態補償只有
「非預設才亮」的琥珀點(L534);新預設「最舊加入」又是反直覺順序(一般清單慣例是新→舊),
手機使用者會看到一串最早的人、且畫面上零線索說明為什麼 → 決定其一並寫進 §4:手機也顯示
當前排序短標籤(晶片已用 grid 疊放取得固定寬,不會抖動),或把 A1 的驗收明文限縮為 sm+
並補一條手機可辨識排序的替代設計。

### P2(建議——不改也能正確交付)

**[P2-1]〔§2.2 預設值〕(架構 + 需求,系統亦確認)** 「三處必須同時改,否則伺服器回聲與
前端快取判斷會漂」的因果不成立:前端三個呼叫一律顯式帶 `sort`(`useReferralData.ts`
L72/L146/L165),伺服器 `parseSortMode` 的回落分支對前端**不可達**,回聲值恆等於請求值
→ 三處照改(對直接打 API、e2e mock 才有意義),但理由改寫為「維持契約一致 / Phase 2 是
API 對外一致性,不影響前端可見行為」,以免實作或回滾時誤判階段依賴。

**[P2-2]〔§2.2 回應形狀變更 / §7 部署偏移〕(系統;與 P1-2 同一事實)** 「後端 schema 是
exact」不成立,真正的約束方向相反:schema 還留著 `subtreeLatestJoinedAt` 而後端停止輸出
才會讓契約測試紅 → 修正理由敘述(結論「同一 commit」仍對),部署偏移的安全論證改為
「前端無 runtime 形狀驗證(`assertShape` 只在 Deno 測試用),故少一個欄位不會炸前端」。

**[P2-3]〔§5 階段切分〕(系統)** 階段 1 與階段 2 會對同一批斷言連續翻兩次:
`network-endpoints.test.ts` L99/L109 與 L162/L164 都是「不帶 `sort` 參數」的呼叫,階段 1
改鍵後期望值變 `[Zoe, Alice, 王]`,階段 2 改預設後又變回 `[王, Alice, Zoe]` → 階段 1 就把
這些順序斷言改成明確帶 `?sort=updated_asc` / `?sort=updated_desc`,讓「排序鍵」與「預設值」
各自只被一個測試釘住,階段 2 只需驗 `sort` 回聲。

**[P2-4]〔§2.2 變更(排序鍵)〕(系統)** plan 寫的替換式 `Date.parse(net.joinedAtOf.get(uid))`
少了現行 `msOf()`(L2343)的 `?? ''` 與 `|| 0` 保護,型別上 `string | undefined` 進
`Date.parse` 直接不過 typecheck,寫成 `?? ''` 又會讓 NaN 進比較器 → 明文指定沿用 `msOf`
風格的 `(Date.parse(x ?? '') || 0)`,並補一個「兩節點 `joinedAt` 完全相同」的測試,把
「升冪 userId 升、降冪(reverse 後)userId 降」這個必然結果釘死(現在無任何測試涵蓋同分)。

**[P2-5]〔§3 架構影響(SWR 快取無需清除)〕(系統)** 「不會先閃一次舊順序」只對「沒選過
排序」的使用者成立:`DataCacheProvider` 用 sessionStorage,F5 後快取仍在,而明示選過
`updated_desc`/`updated_asc` 的使用者 `cached.sort === sortRef.current` 會命中
(`useReferralData` L105),先畫一次舊鍵排出的順序、待背景 revalidate 才更正 → 在 plan 裡
把這個例外寫明(或接受一個 round-trip 的重排),不要把「不會閃」寫成全稱。

**[P2-6]〔§3 架構影響 / §5 Phase 5〕(架構)** `src/utils/referralNetwork.ts` 手抄契約型別,
繞過本專案既有的 `@contract` 慣例(`rewardHistory.ts`、`useRewardData.ts`、
`MemberManagement.tsx`、`RewardHistory.tsx` 都是 `import type { X } from '@contract'`,
只有推薦網絡這組手抄第二份),導致 Phase 5 必須雙寫刪除;實測若只刪 `api-contract.ts` 而
忘了前端那份,`npm run check` 與 `deno task check` **全部照綠**,防線是單向的 → Phase 5
先把 `NetworkNode`/`NetworkSortMode` 改成從 `@contract` re-export,刪欄位收斂成一處。

**[P2-7]〔§2.2 預設值〕(架構)** 預設排序在兩個 runtime 共**四處**硬編碼
(`index.ts` L2393、`referralNetwork.ts` L77、L87、`ReferralTreeView.tsx` L534),規劃書
只把它當「記得同時改」而非收斂成單一來源,且第四處被拆到 §4 當 UI 議題講(同一事實切成兩章
描述,本身就是複本代價的證據)→ 在 `@contract` 匯出 `DEFAULT_NETWORK_SORT`,四處改讀它。
(降級為 P2 的理由:Phase 2/3/4 各有測試守住,照計畫做不會出錯,是長期成本而非本次正確性問題。)

**[P2-8]〔§2.1 現況 Review / §3〕(架構)** 「排序是伺服器權威」在換鍵後首度變成**可選**
架構決策(`joinedAt` 未遮罩、每個節點都有,前端完全排得出來;`referralNetwork.ts` L6–7 的

「無任何讀取端 → 零風險移除」漏掉這層意圖,正當理由應改為「換鍵後 `joinedAt` 已完全取代
它的用途」,否則下一個人會以為預留位是被誤刪的。

**[P2-9]〔§5 階段切分〕(架構)** Phase 3 測試落點標成「(node)」,但

## 需人工裁決

以下為 reviewer 自行標註「不確定是否為真問題 / 需商業判斷」者,**聚合者未定性**:

1. **〔§1 需求 B / §2.2 排序鍵〕(系統)** `joinedAt` 取自 `referral_edges.referred_at`,
   而換推薦人續約時 rewire 只改 `referrer_user_id`、**不更新 `referred_at`**
   (`supabase/migrations/20260724000004_apply_referral_side_effects_pair_history.sql`
   L87–92)——被 rewire 過來的下線帶著更早的時間戳,在新預設 `updated_asc` 下會直接坐上
   該上線清單的第一位,語意是「最早加入我的網絡」但事實不是。
   → 裁決:接受(並在規格書回填時寫明 `joinedAt` = 推薦邊建立時間)或另訂 rewire 的時間語意。

2. **〔§1 需求 A〕(UI/UX)** 「最舊加入」當預設是照單收下,規劃書沒有記錄理由,也沒有
   檢驗長清單情境:一代 roots 由 overview 一次全回、前端 `roots.map` 全數渲染(無分頁/
   虛擬化),下線多的人新加入者永遠沉在最底,手機要滑到底才看得到。
   → 裁決:回填需求方的真實理由(合理推測是「舊→新 ≈ 續約到期先後」,若屬實這個預設
   站得住腳),並確認下線數量大時的預期行為。理由不入檔,下一個人會把它當 bug 改回去。

3. **〔§4 / §6〕(UI/UX)** 整份規劃未評估「是否需要一次性告知」:不只沒存過偏好的人順序
   全反轉,連曾明示選過 `updated_desc` 的人,其「最新加入」語意也從「分支有新血」變成
