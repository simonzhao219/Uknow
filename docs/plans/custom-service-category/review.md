## 發現清單(依嚴重度排序)

### P1

**S1〔§2 資料庫變更〕A4「不產生重複類別」在 UI 之外沒有防線** ——
`listings.category` 是純 `text`,RLS 只查 `user_id` 不查值的形狀;任何繞過
該元件的寫入路徑都能塞進未正規化的近似重複字串,而 `group by` 是逐字元比對。
→ 加最小資料層防線:BEFORE INSERT/UPDATE trigger 正規化空白 + 擋空白字串 + 長度硬上限。

**S2〔§2 資料庫變更〕view 的 `group by` 含內建 30 類,但下拉選單假設「既有自訂類別」只含自訂** ——
「美髮」等內建類別一樣會產生一列,直接渲染 view 原始列會讓內建類別在下拉選單出現兩次。
規劃沒把「自訂類別 = view 回傳列 − `SERVICE_CATEGORIES`」訂成明確規則。
→ 訂為明文規則,並補一條驗收案例。

**S3〔§2 資料流〕只替一條推導路徑做了列數上限防線** ——
規劃以「PostgREST 列數上限會靜默截斷」為由讓表單改查 view,但首頁「就地推導」
正建立在 `HomePage.fetchAllListings`(`select('*')`,無 `limit`)之上,面對同一風險
毫無防線,且它抓的是完整 row、比類別清單更早撞上限。屆時表單列得出某自訂類別、
首頁篩選器卻篩不到任何一筆——正是規劃想避免的「篩了 0 筆的 chip」換條路徑發生,
「保證一致」在跨路徑比較時不成立。
→ 兩條路徑一致處理,或明確記錄為已知限制。

**A1〔§3 + §5〕`EditServiceProvider` 全程沒有測試落點,而它的失效模式是 Create 沒有的** ——
Edit 的 `<Select value={formData.category}>` 從既有刊登讀回(可能已是自訂值),
若 `SelectContent` 只映射內建 30 項,下拉選單配不到 `SelectItem` 而顯示空白;
使用者誤以為類別被清空而手動重選,**覆蓋掉原本的自訂類別**(真實資料損失)。
五階段全綠 + `check:full` 全過,這個缺陷依然被放行。
→ 補測試落點,至少覆蓋「開啟自訂類別刊登的編輯頁,類別正確顯示且可維持不變」。

**U1〔§4 刊登表單〕同一缺陷的 UI/UX 版:非同步載入使競態成為常態** ——
`formData.category` 來自 `listings`,下拉選項來自另一條非同步的 `useCustomCategories`;
規劃明文「載入中或失敗時仍有內建 30 項與『自訂類別…』」——**不含這筆刊登自己正在用的自訂類別**。
LINE 內建瀏覽器等高延遲環境發生機率不低。
→ 不論抓取狀態為何,都保證當前 `category` 值一定對應得到一個可選項。

**A2〔§4 + §7〕拿 report-only 的巡檢當防線佐證** ——
`e2e/test_overflow_sweep.py` 預設 report-only,`E2E_OVERFLOW_STRICT` 不在任何
workflow 設定,不會讓 CI 變紅。§4 表格四個**需要改動**的渲染點裡,階段 5 只有
`FilterChip.test.tsx` 一個會擋 CI,其餘三處 CSS 修正零機械驗證。
這正是 friction-log **同一天**(2026-08-07)記錄的失誤模式:
「把 report-only 的巡檢當成硬闖關的替代品……那是降級不是升級」。
→ 補機械斷言,或明講哪幾處靠人工驗收——不要把 report-only 寫成「都有界」。

**U2〔§4 刊登表單〕漸進揭露後的焦點移轉未定義** ——
透過非同步 state 掛載的欄位若不在原始手勢的呼叫堆疊內同步 `.focus()`,
iOS Safari 經常不彈出軟鍵盤,使用者要自己找到欄位再點一次。
→ 明確指定焦點移轉的實作與驗證方式。

**U3〔§4 溢字防線〕漏列 `DesktopFilterPopover` 的「類別:X」摘要按鈕** ——
沿用 `Button` 基底的 `whitespace-nowrap shrink-0`,無寬度上限;
舊上限 6 字撐得住,10 字會讓按鈕明顯變寬,同列只有搜尋框(`md:flex-1`)會被擠壓,
`md:` 斷點下緣(~768px)有實際風險。又是「手機對、桌機錯」那個失效模式。
→ 補進防線表,加寬度上限或截斷。

**U4〔§5 + §7〕階段 5 沒更新 e2e 巡檢的「最壞但可達」測資** ——
`e2e/test_overflow_sweep.py:56` 所有情境共用 `LONGEST_CATEGORY = "各項運動教練"`
(6 字,註解明寫「`SERVICE_CATEGORIES` 裡最長的」);本功能上線後產品允許的上限
變成 10 字,這支巡檢量到的不再是真正的最壞情況,與它自己宣示的測資原則脫節。
另外 `_setup_listing_create/edit` 從未開啟類別下拉,漸進揭露出的輸入框從未被畫出來過。
→ 一併更新測資。

**U5〔§4 溢字防線〕「補 min-w-0」沒指名補在哪個元素** ——
詳情頁與刊登管理頁兩處都是「無 `flex-1`/`min-w-0` 的文字容器 + 繼承 `shrink-0`
的徽章」並列,且名稱元素都沒有 truncate。只在最外層 `<div>` 補一個 `min-w-0`,
擠壓不會真正解決,只是換位置繼續存在。
→ 比照 `ServiceProviderCard` 的完整組合明確寫出。

**R1〔§1 A6〕「沒人使用」被解讀成「沒有*可見*刊登使用」,這是第二條隱性判斷** ——
停權/過期會員的刊登資料列沒被刪、`category` 也沒清空,但只要他是最後一人,
類別會立刻從全站消失,續約/解除停權後又自動回來。使用者原話「還有一個人使用」
完全沒區分「存在」與「可見」。份量與 §1 已明講的「全站共享詞彙」那條判斷相當,
卻沒被同樣標注。連帶 A6 只寫「改類別/刪除/會籍失效」三種觸發,沒提「停權」;
階段 2 驗證標準也只寫「會籍失效者」不寫「停權者」,而規格書 §5.3 明訂
「提領/credit/刊登可見用同一把尺、三處逐字對齊」的紀律。
→ 把這條判斷明寫進 §1,並把「停權」補進 A6 與階段 2 驗證標準。

### P2

**S4〔§2〕`grant select to anon` 在原規劃中無消費端,且 anon GRANT 測不到** ——
`useCustomCategories` 只被包在 `RequireMembershipRoute` 之後的表單呼叫。
GRANT 驗證落差繼承自 `public_listings` 本身,非本 feature 新增。

**A3〔§3〕`useCustomCategories` 未交代是否比照 `useDataCache` SWR 慣例** ——
`src/hooks/` 既有的資料抓取 hook 一律走 `CachedData` + `MUTATION_GROUPS`。

**A4〔§3〕Create/Edit 本就是逐欄位複製的兩份表單,規劃在兩處各疊同一組新邏輯**。

**U6〔§4〕漏列 `MemberDashboard.tsx:120`**——已被 `CardDescription` 的 truncate 保護,
但清單自稱窮舉,遺漏會讓後人失去警覺。

**U7〔§4 + a11y〕新輸入框沒提 `aria-invalid`/`aria-describedby`** ——
抄的來源(名稱欄位)自己也沒接,非本規劃新增的債,但屬「碰到的檔案順手還債」的低成本機會。

**U8〔§7〕成長風險只談篩選器 chip,沒延伸到表單下拉選單本身** ——
內建 30 + N 個自訂,只靠 `max-h-60` 捲動、無型入即找;Radix typeahead 對注音組字支援有限。
表單這一側其實先碰到。

**R2〔§6 開放問題〕admin 止血手段描述失真** ——
`src/components/admin/` 沒有任何操作 `listings` 的介面,實際得靠工程師連 Supabase Studio 改 row。
